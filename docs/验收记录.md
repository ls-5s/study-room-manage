## 2. 已修复问题

| 问题 | 修复与验证 |
| --- | --- |
| 重叠预约漏拦截 | 使用“已有开始 < 新结束，且已有结束 > 新开始”校验座位和用户冲突；补充边界测试，真实并发抢座仅一人成功 |
| 已开始时段仍可选、预约天数写死 | 按上海时区在开始瞬间禁用，提交前复核；详情页读取公开预约窗口配置 |
| 签到码页面开发依赖加载失败 | 显式预构建 `qrcode`、`jsqr` 并重建开发缓存，页面可加载及生成二维码 |
| 历史快照导致默认趋势和导出失败 | 补结算已有未冻结快照；接口返回日期覆盖信息，图表保留缺口，CSV 携带完整性说明；不按当前容量补造无法追溯的历史数据 |
| 仪表盘单个请求失败清空全部数据 | 各请求独立处理，保留成功部分，失败卡片及图表显示各自错误；修复时未完成页面失败注入复验 |
| 根启动入口缺失 | 新增 `scripts/dev.mjs`；独立端口 43082 / 43083 启动、HTTP 就绪及退出清理通过，默认端口冲突时联动退出 |
| 每日预约上限文案固定 | 公开配置返回实际每日上限，确认页读取配置；加载失败阻止提交，规则测试覆盖上限 1 和 5 |
| 演示数据时间及座位描述矛盾 | `pnpm --dir backend db:repair:demo` 首次校正 2 条、重复运行校正 0 条，保留原值及审计；撤销时间无法还原时明确记录为校正时间，不猜测历史时刻 |
| 首页筛选说明误导及开发残留文案 | 说明日期和起止时间须联动填写、须匹配完整开放时段，移除预约模块未接入的旧说明 |

早期报告中的默认统计故障及两处演示数据矛盾，已有上述后续处理，不能继续作为未修复故障引用。后续补入的历史统计快照属于演示种子，不能作为真实历史容量已恢复的证据。

## 4. 方法、边界与测试数据

- 11 月 12 日的时间推进使用明确标记的隔离数据库夹具及原业务任务，没有修改系统时钟或全局规则；自动完成和部分失约由运行中的调度器触发。这不等于等待完整自习时长的耐久测试。
- 摄像头硬件、手机浏览器权限、多设备与完整无障碍、生产重启与多实例任务竞争、全部非法输入与异常恢复组合仍需专项验证。二维码图片识别、粘贴数据和摄像头取景是不同路径。
- 11 月 19 日页面轮未独立登录普通管理员复测全部权限差异，未完成重复批量生成保护的明确结果确认，也未等待次日生效及完整自动状态推进。
- 测试创建的一次性账号和专用房间已停用，终态预约、工单及审计保留；11 月 12 日测试违约全部撤销，限制清空。
- 11 月 19 日页面轮预约 #66 为学生取消，#69 为管理员取消；工单 #15 已解决、#16 已驳回。预约 #67、#68 在该轮结束时仍已签到，占用当日 16:00–18:00，交由正常业务任务处理；本记录不推断其后续最终状态。
- 历史演示数据与测试数据会进入相应统计，不能作为真实部署效果或完整历史数据恢复的证明。
