## 2. 项目概述

### 2.1 项目背景

高校自习室常采用现场占座或人工登记方式，学生无法提前确认座位是否可用，管理员也难以及时发现占座、预约后未到场和长时间不使用等问题。系统通过线上查询、预约、签到和违约处理，将座位资源从线下人工管理转为可追踪的数字化管理。

### 2.2 建设目标

1. 为学生提供自习室、日期、时段和座位的一站式查询与预约能力。
2. 通过签到、自动释放、违约记录和预约限制减少无效占座。
3. 为管理员提供自习室、座位、预约、反馈和统计数据的统一管理入口。
4. 建立结构清晰、部署简单、适合中小型高校使用的前后端分离系统。
5. 为毕业设计提供完整的需求分析、系统设计、编码、测试和部署实践材料。

### 2.3 用户角色

| 角色       | 主要职责                                                 |
| ---------- | -------------------------------------------------------- |
| 学生       | 浏览资源、预约座位、取消预约、签到、查看记录、提交反馈   |
| 管理员     | 管理用户违约、自习室和座位，处理反馈，查看预约及统计报表 |
| 超级管理员 | 与管理员权限相同，额外负责创建普通管理员                 |
| 系统任务   | 定时处理未签到预约、已结束预约和必要的数据汇总           |

第一版只支持单校区和一个管理员后台，不实现多租户、支付、小程序、消息推送和复杂组织架构。

### 3.3 非功能需求

- **可用性**：常用页面在桌面浏览器宽度 1280px 以上正常使用，移动宽度至少保证核心查询和预约流程可操作。
- **性能**：普通查询接口 P95 响应时间不超过 500ms；预约提交在正常负载下 P95 不超过 1s。
- **一致性**：同一座位同一日期时段只能存在一条有效预约；并发请求不得造成重复占用。
- **安全性**：密码不可明文存储；JWT、权限、输入校验和错误脱敏必须在服务端执行。
- **可维护性**：业务按模块拆分，数据库使用显式迁移，不调用 Sequelize `sync()` 修改生产结构。
- **可观测性**：记录请求方法、状态码、耗时和关键业务事件，不记录密码、Token 和完整个人敏感信息。

## 4. 业务规则与状态机

### 4.1 时间规则

1. 所有 `DATETIME` 统一按 UTC 存储和比较；Sequelize 连接和 MySQL 会话固定 `+00:00`。接口输入、业务日期边界和展示统一转换为 `Asia/Shanghai`，接口时间使用带时区的 ISO 8601 格式。
2. 可预约日期默认为今天及未来 6 个自然日，共 7 个日期；管理员可配置范围，但不得超过 30 个自然日。
3. 时段必须属于自习室开放时段，开始时间早于结束时间，最短 30 分钟，最长 4 小时。
4. 学生每天最多拥有 2 条有效预约；有效预约指待签到或已签到状态。
5. 同一学生在时间区间重叠时不能拥有两个有效预约；时间相邻但不重叠可以预约。
6. 预约开始前 30 分钟至开始后 15 分钟为签到窗口；超过窗口仍未签到即判定失约。
7. 预约开始前学生可取消；开始后学生不能取消。管理员第一版只能取消待签到预约，且必须填写原因；已签到预约等待结束或由后续版本提供独立异常终止流程。
8. 座位维修、停用或所属自习室关闭时不可创建新预约。

### 4.2 预约状态

```text
待签到 ──学生取消──> 已取消
  │
  ├──窗口内签到──> 已签到 ──结束时间到──> 已完成
  │
  └──超过签到窗口──> 已失约
```

数据库中的 `reservation.status` 取值为 `pending`、`checked_in`、`completed`、`cancelled`、`no_show`。状态只能由服务端按流程转换，前端不可直接提交目标状态。每次转换同时写入 `reservation_status_logs`，用于还原详情时间线。

### 4.3 签到规则

- 每个自习室在签到窗口内生成短时有效的二维码核验数据，二维码内容包含 `roomId`、随机 nonce、过期时间和签名，不包含用户密码。
- 服务端验证 JWT 用户身份、二维码签名、二维码归属自习室、当前时间窗口以及用户是否有该自习室的待签到预约。
- 同一预约只能签到一次；重复签到返回 `CONFLICT`。
- 签到二维码长期有效、不设过期时间；管理员展示页每 60 秒换一张图，换图不作废已发出的码。签到码响应禁止缓存，伪造签名一律拒绝。

### 4.4 违约规则

- 系统将 `no_show` 预约写入一条不可重复的违约记录，原因固定为“预约后未在规定时间签到”。
- 默认累计 3 次违约后限制预约 7 天；管理员可以调整阈值和限制天数。
- 已生效的限制区间保存为权威状态；修改规则只影响之后新触发的限制，不追溯改写现有区间。
- 管理员撤销违约时必须填写原因，撤销只改变违约记录状态，不删除审计数据。
- 取消预约不计为违约；管理员因维修或系统故障取消也不计为违约。

### 4.5 反馈工单状态

`待处理 pending -> 处理中 processing -> 已解决 resolved`；`pending` 或 `processing` 也可以转为 `已驳回 rejected`。跳过 `processing` 直接解决返回状态冲突。只有管理员可以改变处理状态，学生只能查看本人提交的工单。

## 5. 总体技术设计

### 5.1 架构

```text
浏览器
  ├─ Vue 3 + TypeScript + Pinia + Vue Router + Axios
  └─ ECharts（管理员统计）
          │ JSON /api/v1
          ▼
Node.js 24 + Express 5
  ├─ 路由层：参数解析、认证和权限中间件
  ├─ 服务层：预约、签到、违约和统计业务规则
  ├─ 数据访问层：Sequelize Model、事务和查询
  ├─ 定时任务：超时预约和到期预约处理
  └─ 统一错误处理与日志
          │ MySQL 8
          ▼
study_room_manage
```

### 5.2 前端约定

- `src/api/` 按模块封装请求；`src/utils/request.ts` 统一设置基础地址、超时、Token 和错误处理。
- `src/stores/` 保存认证用户、Token、全局字典和页面级筛选状态；刷新后通过安全的登录流程恢复状态。
- `src/router/` 配置公开路由、学生路由和管理员路由，使用路由守卫检查登录与角色。
- 页面负责加载态、空状态、错误态和重试；组件负责可复用的表格、座位图、状态标签和表单。
- 所有表单在前端提供即时反馈，服务端仍必须重复校验，不能把前端校验视为安全边界。

### 5.3 后端约定

建议目录：

```text
backend/src/
  config/       环境变量和数据库配置
  models/       Sequelize 模型和关联
  routes/       路由入口和模块路由
  controllers/  HTTP 参数解析和响应
  services/     业务规则和事务
  middleware/   JWT、角色、校验、错误处理
  jobs/         定时任务
  validators/   express-validator 规则
  types/        API 和领域类型
```

路由层不直接拼接复杂业务；事务、冲突校验和状态转换集中在服务层。所有错误转换为现有的 `ApiResponse`，成功响应为 `{ code: 'OK', message, data }`，失败响应为 `{ code, message, data: null }`。

### 5.4 认证与权限

- 登录成功后签发短期 Access Token；Token 使用环境变量中的密钥签名，载荷只放 `userId`、`role` 和过期时间。
- 前端通过 Axios 请求拦截器携带 `Authorization: Bearer <token>`；401 时清除本地会话并跳转登录页。
- 后端按“认证 -> 用户状态 -> 角色 -> 资源归属”顺序检查权限。
- 管理员删除或停用资源时采用软删除或状态停用，保留历史预约和审计记录。

### 5.5 前端设计系统

- 设计 Token 统一定义在 `frontend/src/styles/main.css`，覆盖色彩、字体、间距、圆角、阴影、状态和 Element Plus 变量。
- 首次访问跟随系统明暗主题，用户手动切换后持久保存。
- 桌面端使用玻璃侧栏和 72px 顶栏，移动端使用全高玻璃导航抽屉。
- 学生端使用舒展的编辑式页面层级，管理端使用更紧凑的筛选、表格和指标布局。
- 图表颜色从 CSS 主题 Token 读取，不在具体页面重复维护明暗色值。
- `/admin/design-system` 为管理员设计系统展厅，不依赖后端接口或业务数据。

### 6.2 关联关系

```text
users 1 ── N reservations N ── 1 seats N ── 1 study_rooms

study_rooms 1 ── N room_time_slots
```

### 6.3 约束与索引

- `users.student_no`、`users.username` 唯一；密码只保存 `password_hash`。
- `seats(room_id, seat_no)` 唯一；同一自习室内座位编号不得重复。
- `seats(room_id, row_no, column_no)` 唯一；批次前缀唯一性在锁定房间后的服务层校验。
- `reservations` 对有效状态建立唯一业务约束：同一 `seat_id + reserve_date + slot_id` 只能有一条 `pending` 或 `checked_in` 记录。
- 为 `reservations(user_id, reserve_date, status)`、`reservations(room_id, reserve_date, slot_id)`、`violations(user_id, status)`、`feedback_tickets(status, created_at)` 建立索引。
- MySQL 唯一索引无法直接忽略多个状态时，增加生成列 `active_slot_key`：`pending` 和 `checked_in` 写入座位、日期和时段组合，其他状态写入 `NULL`，再对该列建立唯一索引。
- 预约事务按“用户 -> 自习室 -> 时段 -> 座位”获取锁，资源修改使用相同顺序，避免校验后资源状态被并发改变。
- 历史业务外键默认 `ON DELETE RESTRICT`，禁止通过级联删除破坏预约、签到、违约、反馈和审计历史。
- 所有迁移脚本可重复检查执行结果，禁止业务启动时隐式修改生产表结构。

## 9. 关键实现方案

### 9.1 并发预约

1. 校验请求参数和用户状态。
2. 开启数据库事务，按“用户 -> 自习室 -> 时段 -> 座位”获取锁；用户和座位使用排他锁，自习室和时段使用共享锁。
3. 获得锁后重新校验自习室、时段和座位状态，检查座位预约冲突、学生时间冲突、每日次数和违约限制。
4. 写入预约和初始状态日志并提交事务；任何异常回滚。
5. 依靠唯一约束和 `CONFLICT` 错误兜底，保证高并发下不会出现双重占用。

### 9.2 定时任务

定时任务每分钟运行一次，且每次处理幂等：

- `pending` 且当前时间超过 `startAt + 15 分钟`：更新为 `no_show`，写入违约记录并刷新用户限制。
  超过 30 分钟的候选记录说明任务曾中断、学生在该窗口内可能无法签到，改为转 `cancelled`（`actor=system`）且不记违约，并输出告警等待人工复核。
- `checked_in` 且当前时间超过 `endAt`：更新为 `completed`。
- 所有状态更新使用条件更新，并在同一事务写入状态日志；任务失败只记录错误并在下一周期重试，避免重复计数。

统计模块另有两个每日任务：`00:05` 按日期、房间和时段创建计划容量快照，`01:10` 冻结前一天预约与使用数据。任务未成功创建快照时不得返回伪造的历史利用率。

### 9.3 数据统计

- 预约量：指定时间范围内创建的预约数。
- 签到率：`checked_in + completed` 数量除以有效预约总数。
- 失约率：`no_show` 数量除以有效预约总数。
- 座位利用率：签到预约使用时长除以当日计划开放座位分钟数。`daily_slot_metrics` 在每天 00:05 保存分时段容量，在 01:10 冻结使用数据，避免资源停用后改写历史。
- 所有统计查询按日期范围限制最大 366 天，避免无界查询影响服务。

### 9.4 导出

导出接口复用当前筛选条件，服务端以流式方式生成 UTF-8 BOM CSV，字段使用固定顺序，文件名包含日期范围。导出内容只包含管理员可见字段，不包含密码、Token 等敏感信息。

## 10. 安全、错误处理与运维

### 10.1 安全要求

- 使用 `bcryptjs` 保存密码哈希，禁止日志和响应返回密码或哈希。
- JWT 密钥、数据库密码和管理员初始化凭据只放在后端 `.env`，不得提交 Git。
- 使用 `express-validator` 校验类型、长度、枚举和日期范围；数据库查询使用 Sequelize 参数化条件。
- CORS 只允许当前配置的前端来源；生产环境禁止使用通配符 `*`。
- 对登录、注册、预约和反馈接口增加基础频率限制，防止重复提交和暴力尝试。
- 错误响应不返回 SQL、堆栈、数据库地址和环境变量。

### 10.2 本地部署

```powershell
pnpm --dir backend install --frozen-lockfile
pnpm --dir frontend install --frozen-lockfile
if (-not (Test-Path backend/.env)) { Copy-Item backend/.env.example backend/.env }
if (-not (Test-Path frontend/.env)) { Copy-Item frontend/.env.example frontend/.env }
pnpm --dir backend db:prepare
pnpm dev
```

执行前确认 Docker 中的 `mysql8` 容器运行。数据库准备脚本只负责创建数据库和应用账号；业务表通过显式迁移脚本创建。通过 `http://127.0.0.1:43080/api/v1/health` 和 `http://127.0.0.1:43080/api/v1/ready` 检查服务和数据库状态。

### 10.3 生产部署检查

- 使用生产 `.env`，更新 JWT 密钥、数据库密码和 CORS 来源。
- 先执行迁移，再构建前后端：`pnpm build`。
- 后端使用 `pnpm --dir backend start`，前端使用静态资源服务器托管构建产物。
- 配置 HTTPS、反向代理、数据库备份、日志轮转和进程自动重启。
- 上线前执行健康检查、数据库就绪检查和关键业务冒烟测试。
