## 1.2 编号与图表规则

- 代码：`代码 章-序`，代码题在代码上方，如「代码 5-2 预约创建事务与座位加锁实现」。
- 全文章、图、表、代码的编号必须连续、不跳号、不重号。
- **每一个图表都必须在正文中被显式引用**（「如图 5-3 所示」「见表 4-5」），不允许出现孤立图表。
- 全文只使用一套术语，见 2.4 术语表。

## 1.3 输出格式

- 纯 Markdown 正文，标题用 `#` `##` `###` `####` 四级（`#` 章、`##` 节、`###` 小节、`####` 第 5 章「（一）功能描述」这类五段式小标题），`#` 后必须有空格，不得跳级、不得用加粗代替标题。
- 表格用 Markdown 表格；代码用带语言标记的围栏代码块。
- 截图不生成图片，统一写占位行：`[截图：docs/assets/user-guide/12-my-reservations.png —— 我的预约列表页]`，图题照常编号。
- 不在正文里输出参考文献列表（参考文献单独成节，合并阶段统一生成）。
- 不输出「以下是第 X 章内容」这类解释性文字。

# 2. 写作规则

## 2.1 语体

- 学术书面语，第三人称。禁用「我们」「大家」「你可以」「咱们」。
- 陈述设计用「本文采用」「系统采用」；陈述事实用「该模块负责」；陈述验证用「测试结果表明」。
- 一段一个论点，段首给结论句，后文给依据。段落 3～6 句，句子 15～45 字，长短交替，不写排比句。
- 禁止出现：`赋能`、`闭环`、`多维度`、`深度融合`、`极大地`、`显著提升`、`至关重要`、`不可忽视`、`在当今社会`、`随着……的不断发展`。
- 禁止用「首先/其次/再次/最后」串起整章；小标题之间靠内容递进，不靠序数词连接。
- 不写感叹句、不写设问句、不用比喻，除非该比喻是专业术语。

## 2.2 工程表述

- 区分「设计」与「实现」：第 4 章只讲怎么做设计（结构、模型、规则），不贴大段代码；第 5 章才讲怎么落地（时序、接口、代码、界面）。两章内容不得互相搬运。
- 讲一个功能，按「谁在什么条件下触发 → 系统做什么校验 → 数据怎么变 → 失败怎么处理」四步写，不写「界面美观、操作简便」这类无信息量评价。
- 涉及并发、事务、锁、时区、幂等的地方必须写清楚（这是本课题区别于普通增删改查的地方，是得分点）：预约创建按「用户→自习室→时段→座位」顺序加锁、获得锁后重新校验、唯一约束冲突转 409、DATETIME 按 UTC 存储而业务日期按 Asia/Shanghai、`Idempotency-Key` 防重复提交、签到窗口快照写入预约而不按当前配置重算。
- 状态一律用项目真实枚举：预约 `pending / checked_in / completed / cancelled / no_show`；座位 `available / maintenance / disabled`；违约 `active / revoked`；工单 `pending / processing / resolved / rejected`。不得自造状态名。
- 接口路径一律用真实前缀 `/api/v1/...`，不得写 `/api/xxx` 之类占位。

## 2.3 引用规则

- 正文引用用上标序号 `[1]`，按首次出现顺序编号，与文末参考文献一一对应。
- 只在四种位置引用：研究现状、技术选型依据、同类系统对比、规范与标准。**不得为凑数在无关句子后挂引用**。
- 参考文献必须真实可查。宁少不假：写不满 25 条就写 22 条并说明，绝不允许编造作者、期刊、年份、DOI。
- 中文文献优先来自《计算机应用》《软件导刊》《计算机工程与设计》《现代教育技术》等，也可用硕博学位论文；英文文献用 IEEE/ACM/Elsevier 的会议与期刊。
- 格式示例（注意中文文献用中文标点，作者间用逗号，题名后接文献类型标识）：
  - 期刊：`[1] 张三, 李四. 高校自习室座位预约系统的设计与实现[J]. 软件导刊, 2023, 22(04): 118-123.`
  - 学位论文：`[2] 王五. 基于微服务的高校资源预约平台研究[D]. 成都: 电子科技大学, 2022.`
  - 会议：`[3] CHEN L, WANG H. A seat allocation model for campus study rooms[C]//Proceedings of ICISE 2023. IEEE, 2023: 45-50.`

# 3. 逐章写作指令

> 每章动笔前先输出该章的「小节要点清单」（每节 2～4 条要点 + 图表清单），确认后再展开成文。不要一次性输出全文。

## 第 1 章 绪论（3800～4200 字）

- **1.1 研究背景与研究意义**
  - 1.1.1 研究背景（1100～1300 字）：从高校自习资源供需矛盾切入——扩招后自习需求增长、座位总量有限、现场占座与人工登记的管理方式、预约后不到场造成的资源空转、管理员巡查与登记的工作量。落到「需要一个线上预约与约束机制」。不要从「信息技术迅猛发展」这种万能开头起笔，第一句就要是具体现象或具体矛盾。
  - 1.1.2 研究意义（700～900 字）：分理论意义与实践意义两段。理论意义谈预约制资源分配、失约约束机制在校园场景的适配；实践意义谈对学生的选座效率、对管理员的统计与工单处理、对座位周转率。
- **1.2 国内外研究现状**（1200～1500 字）
  - 1.2.1 国内研究现状：高校图书馆座位预约系统、教务选课式预约、小程序预约的常见做法，指出多数实现偏重「选座」而弱于「失约约束与状态治理」。
  - 1.2.2 国外研究现状：欧美高校 library seat booking、共享空间 desk booking 的商业化产品，强调 calendar 集成与 no-show 惩罚策略。
  - 每小节 2～4 处引用，结尾给一句「现有实现的不足」，为本文的功能设计埋伏笔。不要写成产品罗列。
- **1.3 论文主要研究内容与组织结构**（600～700 字）：列出本文做的四件事（需求与业务规则梳理、数据模型与状态机设计、前后端实现、测试验证），再用一段说明七章如何排布。

> 任何一段如果去掉技术名词后，放到别的系统里也成立，就必须重写。

7. 不把第 3 章写成功能清单，不把第 4 章写成代码说明，不把第 5 章写成操作手册。

# 7. 本提示词的已知局限（写作前请先看）

| 局限 | 影响 | 应对 |
| --- | --- | --- |
| 未包含学校模板文件 | 字号、行距、页边距、封面、页眉页脚、目录样式都不由本提示词决定 | 排版阶段把学院模板（.docx 或 .dot）单独交给排版工具，本提示词只管内容 |
| 参考文献需两轨补 | 开放源能建起大半池子，中文核心仍要人从知网导出 | 见「参考文献」A/B 轨：A 轨先跑，B 轨用知网「导出参考文献」的 GB/T 7714 原文替换 |
| 图表需自行渲染 | PlantUML 源码要丢进渲染器才成图，截图要自己截 | 每个图后附源码；截图按 `docs/assets/user-guide/` 里的真实文件名占位 |
| 页数未精确控制 | 字数与页数是非线性关系，图多则页厚 | 先按 85～95 页估算，定稿排版后再微调图数与用例条数 |
| 第 3～5 章的图号是预算值 | 实际写作中某节可能多出或少掉一张图 | 以连续编号为准，写完每章回头校准全章清单 |
| 不含开题报告、任务书、外文翻译 | 这些是独立材料，结构与论文不同 | 需要时另起提示词，不要塞进本文 |
