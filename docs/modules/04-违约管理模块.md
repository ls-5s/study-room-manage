# 违约管理模块开发文档

> 模块编号：M04  
> 文档版本：V1.3  
> 依赖：[预约与签到](./03-预约与签到模块.md)、[账号权限](./01-认证与用户模块.md)  
> 当前状态：设计完成，待实现

## 1. 模块目标

违约管理模块把预约未签到事件转换为可追溯的违约记录，并根据累计次数限制预约权限。模块处理的是业务后果和人工撤销，不负责判断预约是否超时；超时事件由预约定时任务触发。

必须同时保证：

- 同一预约最多生成一条违约记录。
- 用户看到的次数与后台有效违约记录一致。
- 限制期存在明确的起止时间。
- 管理员撤销违约有原因和审计记录，不物理删除历史。
- 定时任务重复执行不会重复增加次数。

## 2. 数据设计

### 2.1 `violations`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 违约记录 ID |
| `user_id` | BIGINT UNSIGNED | 外键、非空 | 违约用户 |
| `reservation_id` | BIGINT UNSIGNED | 外键、唯一 | 来源预约 |
| `type` | ENUM | 非空 | 第一版固定 `no_show` |
| `status` | ENUM | 非空 | `active`、`revoked` |
| `reason` | VARCHAR(255) | 非空 | 系统或人工说明 |
| `occurred_at` | DATETIME | 非空 | 实际发生时间 |
| `resolved_by` | BIGINT UNSIGNED | 可空 | 撤销操作管理员 |
| `resolved_at` | DATETIME | 可空 | 撤销时间 |
| `resolution_reason` | VARCHAR(255) | 可空 | 撤销原因 |
| `created_at` | DATETIME | 非空 | 创建时间 |
| `updated_at` | DATETIME | 非空 | 更新时间 |

`reservation_id` 唯一是防止重复记违约的核心约束。撤销只修改 `status`，不删除记录。

### 2.2 规则配置

违约配置存入 `system_settings`：

| 配置键 | 默认值 | 范围 |
| --- | --- | --- |
| `violation.threshold` | 3 | 1-20 |
| `violation.restrictionDays` | 7 | 1-90 |

配置值使用 JSON 值列或字符串并经过服务层类型转换。不能将阈值硬编码在路由或前端页面中。

### 2.3 用户字段

`users.violation_count` 表示当前有效违约次数，`users.restriction_started_at` 和 `users.restriction_until` 表示当前限制区间。次数是可由违约记录重算的缓存字段，限制区间是已经被业务事件确认并保存的权威状态，不能根据“最新一条违约 + 当前配置”随时改写。

新增违约时的规则：

```text
activeCount = count(active violations for user)
if activeCount >= threshold:
  restrictionStartedAt = existing future restriction start, or occurredAt
  restrictionUntil = max(existing future restriction end, occurredAt + restrictionDays)
```

已经生效的限制不会因为管理员修改阈值或限制天数而重新计算；新配置只对之后触发的新限制生效。若用户在限制期内再次新增违约，限制截止时间按上述公式延长。

管理员撤销违约后：

1. 重新统计有效违约数。
2. 如果有效违约数仍达到阈值，保留原限制开始和截止时间，不缩短限制。
3. 如果有效违约数低于阈值，清空限制开始和截止时间。
4. 撤销操作和用户字段重算在同一事务中提交。

## 3. 状态与触发

### 3.1 违约记录状态

```text
active
  └─ 管理员撤销并填写原因 -> revoked

revoked
  └─ 终态，不允许学生自行恢复
```

### 3.2 自动触发

预约状态从 `pending` 更新为 `no_show` 后，预约任务调用违约服务：

1. 校验预约确实为 `no_show`。
2. 事务内插入 `violations`，`type=no_show`，`status=active`。
3. 若 `reservation_id` 已存在，说明任务已处理过，保持幂等并结束。
4. 重新统计该用户有效违约数。
5. 达到阈值时按“保留未来限制，并取 `occurredAt + restrictionDays` 与现有限制截止时间的较大值”更新限制区间。
6. 更新用户违约数、限制开始时间和限制截止时间。
7. 提交后记录业务事件日志。

创建违约和更新用户限制必须在同一事务内，否则可能出现记录已写入但用户仍未受限的中间状态。

所有会改变有效违约数或限制区间的流程统一先锁定 `users` 目标行，再操作违约记录。自动触发、管理员撤销和一致性修复共用同一个锁定顺序，避免撤销与新违约并发时覆盖 `violation_count` 或限制截止时间。

## 4. 接口设计

### 4.1 学生查看本人违约

`GET /me/violations`

支持 `status`、`page` 和 `pageSize`。响应同时返回规则摘要和当前限制：

```json
{
  "summary": {
    "activeCount": 2,
    "threshold": 3,
    "restrictionDays": 7,
    "restrictionUntil": null
  },
  "items": [
    {
      "id": 8,
      "reservationId": 1001,
      "type": "no_show",
      "status": "active",
      "reason": "预约后未在规定时间签到",
      "occurredAt": "2026-11-06T08:15:00+08:00",
      "roomName": "图书馆三层自习室",
      "seatNo": "A-01"
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

### 4.2 管理员查询

`GET /admin/violations`

筛选参数：

```text
studentNo
roomId
status
dateFrom
dateTo
page
pageSize
```

管理员详情需要展示来源预约、自习室、座位、时间段、触发时间、撤销人和撤销原因。

### 4.3 撤销违约

`PATCH /admin/violations/:id`

```json
{
  "status": "revoked",
  "reason": "签到设备故障，经核实学生已到场"
}
```

规则：

- 仅管理员可操作。
- 只允许 `active -> revoked`，不能通过该接口创建或恢复违约。
- 原因长度 2-255 字。
- 条件更新状态。若记录已经为 `revoked`，返回 200 和当前记录，不重复更新或写审计；其他非法转换返回 `409`。
- 撤销后重算用户的 `violation_count` 和 `restriction_until`。
- 在同一事务中记录审计日志，包含违约 ID、原状态、目标状态和原因；审计写入失败时整体回滚。

### 4.4 规则配置

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/admin/violation-rules` | 查询当前阈值和限制天数 |
| PUT | `/admin/violation-rules` | 更新配置 |

请求：

```json
{
  "threshold": 3,
  "restrictionDays": 7
}
```

更新仅影响后续违约触发，必须写入审计日志。修改前由前端展示配置影响说明。

## 5. 预约限制检查

创建预约前读取用户和当前时间：

```text
status = active
AND (
  restriction_until IS NULL
  OR restriction_until <= now
)
```

当 `restriction_until > now` 时，创建预约接口返回：

```json
{
  "code": "FORBIDDEN",
  "message": "当前账号处于预约限制期，截止至 2026-11-13 08:15",
  "data": null
}
```

文案不应包含其他用户的违约详情。限制到期后，无需人工清理记录即可继续预约；`violation_count` 仍保留历史有效违约累计值，直到管理员撤销。

这里存在一个产品口径需要固定：累计违约是否永久影响后续次数。本系统采用“每次新增违约后，若当前有效违约数达到阈值，则重新设置限制期”。因此限制到期并不清零历史违约，但只有新增违约才再次触发限制。

## 6. 管理后台页面

`/admin/violations` 包含两个区域：

1. 规则配置卡片：阈值、限制天数、保存按钮和当前配置说明。
2. 违约记录表：学生学号、姓名、来源预约、发生时间、状态、操作。

列表默认按发生时间倒序，支持按日期和状态筛选。撤销弹窗必须要求填写原因，操作成功后刷新列表和用户摘要。

学生端在个人中心和“我的违约”中显示：

- 当前有效违约次数。
- 触发阈值。
- 是否处于限制期及截止时间。
- 每条违约的来源和状态。
- 管理员撤销后的结果。

## 7. 权限与隐私

- 学生只查询本人违约记录。
- 管理员查看违约时仍需避免在列表泄露无关联系方式。
- 撤销原因可能包含人工判断，学生可以看到结果，但内部备注第一版不单独保留。
- 日志只记录违约 ID、用户脱敏标识和操作类型，不记录完整个人信息。

## 8. 数据一致性修复

为防止缓存字段与违约记录不一致，系统基础模块提供受控修复命令：

```text
pnpm --dir backend violations:reconcile
```

命令按用户重算 `violation_count`，并校验 `restriction_until` 是否存在、是否与当前有效违约数一致，输出差异数量和用户 ID。修复规则如下：

- 有效违约数达到阈值但限制区间缺失时，按最近一次有效违约和当时的配置重建，并写入告警。
- 有效违约数低于阈值但限制区间仍存在时，清空限制。
- 有效违约数仍达到阈值且限制区间存在时，保留原区间，不以当前规则重算。

定期任务可以每天运行一次轻量校验；第一版按需执行，不在每分钟任务里全量扫描。

## 9. 测试用例

1. 预约超时后生成一条有效违约记录。
2. 同一任务重复运行不生成第二条违约。
3. 达到阈值后用户被限制预约，接口返回截止时间。
4. 未达到阈值时只累计次数，不限制预约。
5. 限制到期后用户可以重新预约。
6. 管理员撤销违约后状态改为 `revoked`，次数下降。
7. 撤销后低于阈值时限制截止时间清空。
8. 学生不能撤销自己的违约，也不能查看他人违约。
9. 管理员撤销必须填写原因。
10. 阈值和限制天数越界时配置失败。
11. 撤销操作重复提交不会重复改变次数。
12. 违约记录与用户缓存重算结果一致。
13. 用户有 4 条有效违约、撤销其中 1 条后仍达到阈值时，原限制截止时间不缩短。
14. 修改阈值或限制天数不会改变已经生效的限制区间。
15. 管理员撤销违约与新失约记录并发提交时，按用户锁串行执行，最终次数等于有效违约记录数。
