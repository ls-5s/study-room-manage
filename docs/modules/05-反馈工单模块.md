# 反馈工单模块开发文档

> 模块编号：M05  
> 文档版本：V1.3  
> 依赖：[账号权限](./01-认证与用户模块.md)、[自习室与座位](./02-自习室与座位模块.md)  
> 当前状态：设计完成，待实现

## 1. 模块目标

反馈工单模块为学生提供占座举报和使用问题反馈渠道，为管理员提供核实、处理和结果记录入口。它不是在线聊天工具，也不用于修改预约或替代违约判定。

第一版覆盖：

- 占座举报。
- 座位或自习室设施问题。
- 环境与卫生问题。
- 其他使用问题。

第一版不支持附件上传、匿名反馈、实时对话和工单分派。管理员身份和完整处理轨迹仍须可追溯。

## 2. 数据设计

### 2.1 `feedback_tickets`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 工单 ID |
| `user_id` | BIGINT UNSIGNED | 外键、非空 | 提交学生 |
| `room_id` | BIGINT UNSIGNED | 外键、可空 | 相关自习室 |
| `seat_id` | BIGINT UNSIGNED | 外键、可空 | 相关座位 |
| `room_name_snapshot` | VARCHAR(64) | 可空 | 提交时的自习室名称 |
| `seat_no_snapshot` | VARCHAR(32) | 可空 | 提交时的座位编号 |
| `type` | ENUM | 非空 | 工单类型 |
| `description` | TEXT | 非空 | 问题描述 |
| `status` | ENUM | 非空 | 四种工单状态 |
| `result` | TEXT | 可空 | 管理员处理结果 |
| `handled_by` | BIGINT UNSIGNED | 可空 | 最近处理管理员 |
| `processed_at` | DATETIME | 可空 | 首次开始处理时间 |
| `closed_at` | DATETIME | 可空 | 解决或驳回时间 |
| `created_at` | DATETIME | 非空 | 提交时间 |
| `updated_at` | DATETIME | 非空 | 更新时间 |

工单类型：

| 值 | 展示名称 | 典型场景 |
| --- | --- | --- |
| `occupied_seat` | 占座举报 | 座位长期放置物品但无人使用 |
| `equipment` | 设施问题 | 台灯、插座、桌椅损坏 |
| `environment` | 环境问题 | 噪声、卫生、温度 |
| `other` | 其他问题 | 无法归入以上类型 |

### 2.2 约束与索引

- `feedback_tickets(user_id, created_at)`。
- `feedback_tickets(status, created_at)`。
- `feedback_tickets(room_id, seat_id)`。
- 提交时如果提供 `seatId`，其必须属于对应 `roomId`。
- 提交事务中把当时的自习室名称和座位编号写入快照字段；详情和列表优先显示快照值，避免资源改名后历史工单被错误描述。
- 原始描述、资源 ID 和资源名称快照在工单创建后不可修改。
- 有处理记录的工单不物理删除。

## 3. 状态机

```text
pending
  ├─ 管理员开始处理 -> processing
  └─ 管理员直接驳回 -> rejected

processing
  ├─ 管理员填写处理结果 -> resolved
  └─ 管理员说明原因 -> rejected

resolved / rejected
  └─ 终态
```

| 当前状态 | 目标状态 | 必填字段 |
| --- | --- | --- |
| `pending` | `processing` | 无 |
| `pending` | `rejected` | `result` |
| `processing` | `resolved` | `result` |
| `processing` | `rejected` | `result` |
| `resolved/rejected` | 任意状态 | 不允许 |

第一版不支持学生补充内容或重新打开工单。如果需要后续沟通，管理员可在处理结果中说明，学生可重新提交新工单。

管理员详情中的处理时间线读取 `audit_logs` 中 `resource_type=feedback_ticket`、`resource_id=工单 ID` 的记录，结合 `created_at`、`processed_at` 和 `closed_at` 展示。学生端只展示当前状态、结果和对外时间字段，不返回内部审计快照。

## 4. 接口设计

### 4.1 提交反馈

`POST /feedback-tickets`

```json
{
  "type": "occupied_seat",
  "roomId": 12,
  "seatId": 205,
  "description": "A-01 座位从上午开始一直放置物品，现场无人使用。"
}
```

校验：

- `type` 必须为四个枚举值之一。
- `description` 去除首尾空白后长度 5-1000 字。
- 占座举报必须提供 `roomId` 和 `seatId`。
- 其他类型至少提供 `roomId` 或 `description` 足以描述问题；若提供座位必须校验归属。
- 学生不能在提交接口指定 `status`、`userId`、`handledBy`。
- 每个用户每分钟最多提交 3 条、每小时最多提交 10 条；超过返回 429、`RATE_LIMITED` 和 `Retry-After`。

成功返回 201、工单编号和初始状态 `pending`。

### 4.2 学生查询

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/me/feedback-tickets` | 查询本人工单 |
| GET | `/me/feedback-tickets/:id` | 查看本人工单详情 |

列表支持 `status`、`type`、`page` 和 `pageSize`。详情返回自习室名称、座位编号、提交内容、当前状态、处理结果和关键时间。

### 4.3 管理员处理

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/admin/feedback-tickets` | 查询全部工单 |
| GET | `/admin/feedback-tickets/:id` | 查看工单详情 |
| PATCH | `/admin/feedback-tickets/:id` | 更新状态和处理结果 |

更新请求：

```json
{
  "status": "resolved",
  "result": "已现场核实，物品已由管理员联系物主取走。"
}
```

服务端：

1. 锁定或条件读取工单。
2. 检查当前状态是否允许目标状态。
3. 检查目标状态所需的结果内容。
4. 更新 `status`、`result`、`handled_by` 和对应时间。
5. 在同一事务中写入审计日志；审计写入失败时整体回滚。

管理员列表支持 `status`、`type`、`roomId`、日期范围、学号和关键字。默认排序为待处理优先，再按提交时间升序，避免旧工单长期积压。

## 5. 服务层规则

建议拆分：

```text
feedback.service.ts
  createTicket(currentUser, input)
  listMyTickets(currentUser, filter)
  getMyTicket(currentUser, id)
  listAdminTickets(filter)
  transitionTicket(admin, id, input)
```

状态转换使用集中白名单，不允许控制器自行判断：

```text
pending    -> processing, rejected
processing -> resolved, rejected
```

资源归属检查在服务层完成。管理员可以读取全部工单，但响应不返回学生密码、邮箱以外的非必要隐私字段。

## 6. 前端页面

### 6.1 学生提交 `/feedback`

- 类型选择、自习室选择、座位选择、描述。
- 选择占座举报后房间和座位变为必填。
- 提供清晰的成功结果和工单编号。
- 表单错误保留用户已输入内容，提交失败不应清空。
- 支持查看“我的反馈”标签页。

### 6.2 我的反馈

- 状态筛选：待处理、处理中、已解决、已驳回。
- 列表显示类型、房间/座位、提交时间和最新状态。
- 详情展示处理结果；未处理时不显示空白结果框。
- 已解决和已驳回为不同视觉状态，不能都显示为成功。

### 6.3 管理员反馈处理 `/admin/feedback`

- 左侧或顶部显示待处理数量。
- 支持按状态、类型、房间、日期和关键词筛选。
- 详情抽屉包含来源、描述和状态时间线。
- “开始处理”“标记解决”“驳回”按钮按当前状态显示。
- 解决或驳回必须填写结果，提交中禁用重复操作。

## 7. 权限与隐私

- 学生只能创建和读取本人反馈。
- 学生不能读取内部管理员 ID。
- 管理员不能修改原始描述和提交人。
- 公共接口不得返回反馈全文，避免未授权读取学生信息。
- 日志不记录完整问题描述，只记录工单 ID、类型和状态变化。
- 结果文案不得包含其他学生个人信息。

## 8. 异常与边界

| 场景 | 处理 |
| --- | --- |
| 学生访问他人工单 | 固定返回 `404 NOT_FOUND`，不泄露是否存在 |
| 工单已解决再次处理 | 409 状态冲突 |
| 跳过处理中直接解决 | 固定返回 `409 CONFLICT`，必须先经过 `processing` |
| 驳回时未填写结果 | 422 校验错误 |
| 座位与自习室不匹配 | 422 |
| 房间已停用或改名但历史工单仍存在 | 允许查看，显示 `room_name_snapshot` 和 `seat_no_snapshot` |
| 重复快速提交 | 客户端防抖加服务端限流 |

对于“跳过处理中直接解决”，本文采用严格规则：必须先进入 `processing`，再标记 `resolved`。这保证处理过程有开始时间和操作人。

## 9. 测试用例

1. 学生提交有效占座举报，返回待处理工单。
2. 占座举报缺少座位时校验失败。
3. 服务端忽略客户端传入的 `userId` 和 `status`。
4. 学生只能看到本人的反馈列表和详情。
5. 管理员按状态和房间筛选工单。
6. `pending -> processing` 成功。
7. `processing -> resolved` 需要处理结果。
8. `processing -> rejected` 需要驳回原因。
9. 跳过 `processing` 直接解决被拒绝。
10. 终态工单不能再次修改。
11. 工单详情显示正确房间和座位。
12. 工单状态变化写入审计日志。
13. 学生访问他人工单时固定返回 404，不泄露资源是否存在。
14. 审计写入失败时工单状态转换整体回滚。
15. 提交后修改自习室名称和座位编号，历史工单仍显示提交时的资源名称。
16. 超过每分钟或每小时提交上限时返回 429，且不创建工单。
