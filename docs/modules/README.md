## 1. 文档定位

上位文档说明项目背景、总体需求、技术选型和交付计划。本目录按业务模块继续展开，形成可以直接指导数据库迁移、后端接口、前端页面和测试用例编写的开发文档。

模块文档遵循以下原则：

1. 一个业务模块对应一个 Markdown 文件，模块内同时描述数据、接口、页面、业务规则和验收点。
2. 跨模块共用的时间、权限、响应格式和事务约定放在本文件中，模块文档只引用，不重复改写。
3. “当前基线”和“计划实现”明确区分，避免把设计内容误写成已经完成的功能。
4. 模块之间的数据依赖只通过稳定字段和公开服务方法连接，页面不直接依赖其他模块的内部实现。

## 5. 公共接口约定

### 5.1 地址与响应

- API 前缀统一为 `/api/v1`。
- 请求和响应使用 `application/json`，文件导出除外。
- 成功响应：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {}
}
```

- 失败响应：

```json
{
  "code": "VALIDATION_ERROR",
  "message": "请检查输入内容",
  "data": null
}
```

- 分页数据统一放在 `data` 中：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0
}
```

- 列表默认 `page=1`、`pageSize=20`，`pageSize` 最大为 100。排序参数必须使用服务端白名单，不能直接拼接为 SQL。

### 5.2 HTTP 状态与错误码

| 场景               | HTTP 状态 | `code`                 |
| ------------------ | --------- | ---------------------- |
| 查询或操作成功     | 200/201   | `OK`                   |
| 参数格式或枚举错误 | 400       | `BAD_REQUEST`          |
| 字段校验失败       | 422       | `VALIDATION_ERROR`     |
| 未登录、Token 失效 | 401       | `UNAUTHORIZED`         |
| 角色不符或越权访问 | 403       | `FORBIDDEN`            |
| 资源不存在         | 404       | `NOT_FOUND`            |
| 状态冲突、重复预约 | 409       | `CONFLICT`             |
| 请求频率超过限制   | 429       | `RATE_LIMITED`         |
| 数据库暂不可用     | 503       | `DATABASE_UNAVAILABLE` |
| 未处理异常         | 500       | `INTERNAL_ERROR`       |

业务错误信息由后端提供面向用户的简洁文案。SQL、堆栈、表名、数据库地址和字段哈希不得出现在响应中。

### 5.3 认证与权限顺序

需要登录的接口按以下顺序检查：

1. 从 `Authorization: Bearer <token>` 解析 Token。
2. 验证签名、过期时间和会话是否已撤销。
3. 查询用户，检查账号状态。
4. 检查角色是否具备接口访问权限。
5. 对预约、反馈等资源检查 `resource.userId === currentUser.id`。
6. 管理员越权能力必须由单独路由和权限中间件显式授予。

未登录返回 `UNAUTHORIZED`，已登录但无权限返回 `FORBIDDEN`。客户端不得仅依靠隐藏按钮实现权限控制。

## 6. 公共业务约定

### 6.1 时间

- 所有 `DATETIME` 按 UTC 存储和比较；业务日期字段使用 `DATE`，表示 `Asia/Shanghai` 下的自然日。
- `room_time_slots.start_time` 和 `end_time` 使用 `TIME`，表示东八区本地作息时间，不是 UTC 时刻；预约服务将业务日期与时段组合为东八区时间后再转换为 UTC 保存。
- Sequelize 连接固定 `timezone: '+00:00'`，MySQL 连接会话固定 `time_zone='+00:00'`，应用进程不得依赖机器本地时区。
- 接口时间使用带时区的 ISO 8601，例如 `2026-11-10T08:00:00+08:00`。
- 输入解析、`startOfDay`、`endOfDay` 和展示转换统一使用 `Asia/Shanghai`，内部比较统一使用 UTC。
- 预约日期使用 `YYYY-MM-DD`，并与 `startAt`、`endAt` 的本地日期一致。
- 所有服务端时间判断以注入的 `now()` 为入口，便于测试签到窗口、超时和定时任务。
- 测试必须覆盖本地时间 `23:59` 跨 UTC 日期的情况，禁止使用 `new Date('YYYY-MM-DD')` 直接解析业务日期。

### 6.2 状态枚举

| 领域     | 字段     | 可选值                                                       |
| -------- | -------- | ------------------------------------------------------------ |
| 用户     | `role`   | `student`、`admin`、`super_admin`                            |
| 用户     | `status` | `active`、`disabled`                                         |
| 自习室   | `status` | `open`、`closed`、`disabled`                                 |
| 开放时段 | `status` | `active`、`inactive`                                         |
| 座位     | `status` | `available`、`maintenance`、`disabled`                       |
| 预约     | `status` | `pending`、`checked_in`、`completed`、`cancelled`、`no_show` |
| 违约记录 | `status` | `active`、`revoked`                                          |
| 反馈工单 | `status` | `pending`、`processing`、`resolved`、`rejected`              |

枚举只由服务端状态转换方法写入。前端不能提交预约、违约或工单的任意目标状态。

### 6.3 资源归属

- 学生只能创建和查询本人的预约、违约与反馈。
- 学生只能查询公开的自习室、开放时段和座位摘要。
- 管理员可以查询管理范围内的业务记录，但不能读取密码哈希、Token 和二维码签名密钥。
- 记录被停用后仍保留历史关联；有历史数据的自习室、时段或座位不得物理删除。

### 6.4 事务边界

- 预约创建、取消、签到、失约处理和管理员关键操作必须使用事务。
- 事务中先完成权限和资源状态校验，再执行状态更新。
- 预约创建统一按“用户 -> 自习室 -> 时段 -> 座位”获取锁：用户和座位使用排他锁，自习室和时段使用共享锁；获得锁后必须重新读取并校验资源状态，不能复用加锁前的快照。取消预约同样先锁用户行，再更新预约，保证每日次数统计与写入串行。
- 自习室和时段必须用主键等值查询加锁，禁止用 `room_id` 等范围条件加共享锁，避免 `REPEATABLE READ` 下的间隙锁造成同房间不同座位互相阻塞。
- 管理员修改自习室、时段或座位时使用写事务并更新目标资源，依靠与预约事务相同的资源锁顺序避免状态在校验和插入之间变化。
- 捕获唯一约束冲突后统一转换为 `409 CONFLICT`，不向前端暴露数据库错误。
- 管理员关键业务的审计记录与业务状态更新在同一数据库事务中提交；审计写入失败时整体回滚。
- 普通访问日志和业务指标事件可在事务提交后写入，此类日志失败不回滚业务，但必须告警。

### 6.5 数据库迁移

- 当前 `db:prepare` 只负责数据库和应用账号，不创建业务表。
- 本目录各模块的数据表应由按顺序编号的迁移文件创建和修改。
- 每次迁移同时提供回滚说明。生产环境禁止在应用启动时调用 `sequelize.sync()`。
- 字段新增优先采用可向后兼容方式；删除或重命名字段必须经过数据迁移和版本发布检查。
- 外键默认使用 `ON DELETE RESTRICT`、`ON UPDATE RESTRICT`；业务资源通过状态停用，不使用 `ON DELETE CASCADE` 删除历史预约、签到、违约、反馈或审计记录。
- 确有删除需求的非历史数据必须由专用清理任务按明确范围处理，不能由用户接口直接删除。
- 返回 429 时同时提供 `Retry-After` 秒数；前端按该时间显示等待提示，不自动循环重试。

## 10. V1.1 修订说明

本次审查后固定了以下跨模块决策：

1. `DATETIME` 统一按 UTC 存储，业务日期和接口展示使用 `Asia/Shanghai`。
2. 预约创建与资源维护使用相同的资源锁顺序，获得锁后重新校验状态。
3. 自习室列表区分静态可预约座位数和指定日期时段的动态可用座位数。
4. 增加 `reservation_status_logs`，预约时间线不再依赖 `updated_at` 推断。
5. 已生效违约限制保存为权威区间，规则修改不追溯改写；已签到预约不能复用取消状态。
6. 增加 `daily_slot_metrics`，按日期、房间和时段冻结容量及使用数据。
7. 管理员关键操作与审计记录同事务提交，历史外键默认拒绝级联删除。
8. 越权读取、重复撤销和非法状态转换改为确定的状态码，避免实现时二选一。

## 11. V1.2 修订说明

本轮继续固定三个实现边界：

1. 跨自习室按统一开始、结束时间筛选，每个房间匹配自己的时段，不再共用一个 `slotId`。
2. 历史统计改用 `daily_slot_metrics`，保存日期、房间和时段三个维度，并在 00:05 冻结当天的计划容量。
3. 结构性资源变更从次日生效；关闭、维修等停止预约的状态可以当天立即生效，但不能修改当天的计划容量分母。

## 14. V1.5 修订说明

本轮实现 M04 违约管理，并同步 M03、M07 的跨模块契约：
