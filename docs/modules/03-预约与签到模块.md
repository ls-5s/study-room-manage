## 1. 模块目标

预约与签到模块是系统的核心业务闭环，负责将可预约座位转换为有明确时间范围和使用状态的学生预约。

模块需要同时解决四类问题：

1. 资源竞争：同一座位同一时段不能出现两条有效预约。
2. 用户冲突：同一学生不能同时预约两个座位，也不能无限囤积预约。
3. 状态流转：预约必须按照待签到、已签到、已完成、已取消或已失约转换。
4. 到场核验：学生只能在签到窗口内使用指定自习室的有效签到码完成签到；签到码不可用时，管理员可以人工核验到场。

## 2. 核心规则

| 规则 | 默认值 | 配置方式 |
| --- | --- | --- |
| 可预约提前天数 | 今天及未来 6 天，共 7 天 | 系统设置，最大 30 天 |
| 学生每日有效预约上限 | 2 条 | 系统设置 |
| 签到窗口开始 | 预约开始前 30 分钟 | 第一版固定常量 |
| 签到窗口结束 | 预约开始后 15 分钟 | 第一版固定常量 |
| 二维码有效期 | 长期有效，不设过期时间 | 固定规则 |
| 二维码换图 | 展示页每 60 秒换一张（换图不影响已发出的码） | 固定常量 |
| 失约任务停机豁免 | 30 分钟 | 固定常量 |
| 创建与取消频率 | 每用户每分钟 10 次 | 系统设置 |
| 重复签到 | 拒绝 | 固定规则 |
| 开始后学生取消 | 拒绝 | 固定规则 |
| 管理员取消 | 必须填写原因 | 固定规则 |
| 学生改签座位或时段 | 不支持，必须取消后重新预约 | 第一版固定 |

有效预约仅指 `pending` 和 `checked_in`。已取消、已完成和已失约不占用每日预约次数，也不阻止新的不重叠预约。

房间、时段和座位还必须满足 `bookable_from <= reserveDate`。资源展示与预约创建调用同一个资源生效判断，不能把“次日生效”只写在前端。

签到窗口的两个边界在创建预约时写入快照（`check_in_open_at`、`check_in_deadline`）。窗口时长第一版固定，但历史预约的窗口不会因为以后调整常量而漂移；签到、失约任务和前端展示都只读快照字段，不重新用当前配置推导。

### 2.1 时间与归属口径

- `reserve_date` 是唯一业务归属维度。签到、失约、取消、统计一律按 `reserve_date` 归属，不使用 `checked_in_at` 的日历日期。
- 若某时段开始时间早于 `00:30`，其签到窗口会落在前一个自然日。这种签到记录的业务日期仍是 `reserve_date`；`check_ins.checked_in_at` 只作为审计时间，不参与按天汇总。
- 所有时间判断通过注入的 `now()` 完成，SQL 中不得写入数据库当前时间函数；定时任务的查询条件把 `now` 作为绑定参数，并在比较列的常量侧做运算。

## 4. 数据设计

### 4.1 `reservations`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 预约 ID |
| `user_id` | BIGINT UNSIGNED | 外键、非空 | 预约学生 |
| `room_id` | BIGINT UNSIGNED | 外键、非空 | 自习室 ID |
| `seat_id` | BIGINT UNSIGNED | 外键、非空 | 座位 ID |
| `slot_id` | BIGINT UNSIGNED | 外键、非空 | 开放时段 ID |
| `room_name_snapshot` | VARCHAR(64) | 非空 | 创建预约时的自习室名称 |
| `room_location_snapshot` | VARCHAR(128) | 非空 | 创建预约时的自习室位置 |
| `seat_no_snapshot` | VARCHAR(32) | 非空 | 创建预约时的座位编号 |
| `reserve_date` | DATE | 非空 | 预约业务日期 |
| `start_at` | DATETIME | 非空 | 预约开始时间快照，UTC |
| `end_at` | DATETIME | 非空 | 预约结束时间快照，UTC |
| `check_in_open_at` | DATETIME | 非空 | 签到窗口开始时间快照，UTC |
| `check_in_deadline` | DATETIME | 非空 | 签到窗口结束时间快照，UTC |
| `status` | ENUM | 非空 | `pending`、`checked_in`、`completed`、`cancelled`、`no_show` |
| `idempotency_key` | VARCHAR(64) | 可空 | 创建请求幂等键 |
| `cancel_reason` | VARCHAR(255) | 可空 | 取消原因 |
| `cancelled_by` | BIGINT UNSIGNED | 可空 | 取消操作人；系统取消时为空 |
| `cancelled_at` | DATETIME | 可空 | 取消时间，UTC |
| `created_at` | DATETIME | 非空 | 创建时间，UTC |
| `updated_at` | DATETIME | 非空 | 更新时间，UTC |

`room_id`、`seat_id`、`slot_id` 冗余在预约表中是刻意的：直接查询方便，且创建时已验证座位属于自习室、时段属于自习室。名称、位置和编号快照用于历史展示，资源之后改名不会改变学生已创建预约的描述。

`check_in_open_at` 和 `check_in_deadline` 由 `start_at` 与固定窗口偏移计算后落库，**不在查询时用当前配置重算**。这样后续调整窗口时长只影响新预约，历史记录仍可解释“当时应该在几点前签到”。

`idempotency_key` 由客户端在请求头 `Idempotency-Key` 提供，只在单个用户内唯一。相同用户重复提交同一键必须返回首次创建的预约，不得再插入一条记录，也不得消耗额度。

### 4.2 `check_ins`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 签到记录 ID |
| `reservation_id` | BIGINT UNSIGNED | 唯一、外键 | 对应预约 |
| `checked_in_at` | DATETIME | 非空 | 实际签到时间，UTC |
| `business_date` | DATE | 非空 | 冗余的 `reserve_date`，用于按天统计 |
| `method` | ENUM | 非空 | `qr`、`manual` |
| `nonce` | CHAR(36) | 可空 | 二维码随机标识；人工核验为空 |
| `operator_id` | BIGINT UNSIGNED | 可空 | 人工核验时的操作管理员；二维码签到为空 |
| `remark` | VARCHAR(255) | 可空 | 人工核验说明 |
| `created_at` | DATETIME | 非空 | 记录创建时间，UTC |

`reservation_id` 唯一保证同一预约只有一条签到记录。签到成功后预约状态同时变为 `checked_in`，两者必须在同一事务中提交。

`nonce` 的语义是**防伪与审计标记，不是一次性凭据**。同一房间的二维码在有效期内被多名学生共用，同一个 `nonce` 必然重复出现在多条签到记录中。重放防护由 `reservation_id` 唯一约束加预约状态条件更新承担，不能给 `nonce` 加唯一索引，也不能做“nonce 已被使用即拒绝”的判断。

`business_date` 冗余是为了让按业务日期汇总不依赖 `checked_in_at` 的日历日；它与所属预约的 `reserve_date` 必须一致，由服务写入。

### 4.3 `reservation_status_logs`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 状态日志 ID |
| `reservation_id` | BIGINT UNSIGNED | 外键、非空 | 对应预约 |
| `from_status` | ENUM | 可空 | 创建记录时为空 |
| `to_status` | ENUM | 非空 | 转换后的状态 |
| `actor_type` | ENUM | 非空 | `user`、`admin`、`system` |
| `actor_id` | BIGINT UNSIGNED | 可空 | 系统任务时为空 |
| `reason` | VARCHAR(255) | 可空 | 取消或系统处理原因 |
| `occurred_at` | DATETIME | 非空 | 状态转换时间，UTC |

创建预约、取消、签到、失约和完成都必须在同一业务事务中写入状态日志。预约详情的时间线只读取该表，不使用可能被后续更新覆盖的 `reservations.updated_at` 推断历史。

索引与约束：

- `UNIQUE(reservation_id, to_status)`：把“每次转换只写一条业务事件”变成数据库约束。终态不可再转换，因此该唯一键不会被合法业务挡住；它挡的是事务重试和并发重复写入。
- `reservation_status_logs(reservation_id, occurred_at)`。
- `reservation_status_logs(to_status, occurred_at)`，用于状态审计。

### 4.4 有效预约唯一键

必须增加数据库生成列，并建立唯一索引：

```sql
ALTER TABLE reservations
  ADD COLUMN active_slot_key VARCHAR(96)
    AS (
      CASE
        WHEN status IN ('pending', 'checked_in')
          THEN CONCAT(seat_id, ':', DATE_FORMAT(reserve_date, '%Y-%m-%d'), ':', slot_id)
        ELSE NULL
      END
    ) STORED,
  ADD UNIQUE KEY uk_reservations_active_slot (active_slot_key);
```

要点：

- MySQL 唯一索引允许多个 `NULL`，因此已取消、已完成和已失约历史不会妨碍后续预约。
- 生成列必须显式给出类型和长度（`VARCHAR(96)`），并对 `reserve_date` 使用 `DATE_FORMAT` 固定格式，避免隐式转换产生不稳定字符串。
- 生成列在 MySQL 中只能引用本表列，且不能用 `NOW()` 等非确定函数；该定义满足要求。
- Sequelize 的模型同步不擅长表达生成列，必须使用显式迁移中的 `queryInterface.sequelize.query()` 执行原始 SQL，并在迁移回滚中先删唯一索引再删列。
- 该唯一键依赖开放时段不重叠。项目必须在时段维护服务中禁止同一自习室的有效时段重叠；迁移完成后必须执行一致性校验（统计同房间有效时段两两重叠数，结果必须为 0），并把该检查纳入种子数据和 CI。如果未来允许重叠，必须改用排他约束或专用锁表，不能保留现有唯一键。

该唯一键是“同一座位同一时段只能有一条有效预约”的最后一道保险，不是唯一手段：创建事务的座位行锁、应用层冲突查询和唯一键三层都要有。

### 4.5 索引

- `reservations(user_id, reserve_date, status)`。
- `UNIQUE(reservations.user_id, idempotency_key)`。
- `reservations(room_id, reserve_date, slot_id, status)`。
- `reservations(seat_id, reserve_date, status)`。
- `reservations(status, check_in_deadline)` 用于失约任务；条件写成 `check_in_deadline < :now - INTERVAL 30 MINUTE`，保持常量侧运算。
- `reservations(status, end_at)` 用于完成任务。
- `check_ins(business_date)` 用于按业务日期统计。

## 5. 接口设计

### 5.0 通用约定

- 所有响应使用 [模块公共约定](./README.md#51-地址与响应) 的统一信封 `{ code, message, data }`，包括 4xx 和 5xx。
- 列表统一返回 `data = { items, page, pageSize, total }`。
- 需要登录的接口先认证再鉴权；失败分别返回 `401 UNAUTHORIZED` 和 `403 FORBIDDEN`。
- 时间字段使用带时区的 ISO 8601（`+08:00`），服务端内部按 UTC 存储。
- 写接口返回 `Cache-Control: no-store`。

### 5.1 创建预约

`POST /reservations`

请求头：

```text
Authorization: Bearer <token>
Idempotency-Key: 5c1e2f0a-9f3a-4b0e-8f0e-2f6e7f0b1c22
```

请求体：

```json
{
  "roomId": 12,
  "seatId": 205,
  "reserveDate": "2026-11-10",
  "slotId": 31
}
```

`Idempotency-Key` 必填，长度 8-64，只允许 `[A-Za-z0-9_-]`。首次提交返回 `201`；同一用户用相同键重放返回 `200`，`data.replayed=true` 并附首次创建的预约，不新增记录、不重复计次。同一个键配上不同的请求参数（例如换了座位）返回 `422 VALIDATION_ERROR`，避免客户端复用一个键却以为换到了别的座位。

响应：

```json
{
  "code": "OK",
  "message": "预约创建成功",
  "data": {
    "id": 1001,
    "replayed": false,
    "roomId": 12,
    "seatId": 205,
    "seatNo": "A-01",
    "reserveDate": "2026-11-10",
    "startAt": "2026-11-10T08:00:00+08:00",
    "endAt": "2026-11-10T10:00:00+08:00",
    "status": "pending",
    "checkInWindow": {
      "openAt": "2026-11-10T07:30:00+08:00",
      "deadline": "2026-11-10T08:15:00+08:00"
    }
  }
}
```

### 5.3 取消预约

`POST /reservations/:id/cancel`

学生请求：

```json
{
  "reason": "临时有课"
}
```

管理员请求：

```json
{
  "reason": "自习室设备故障，统一取消"
}
```

规则：

- 学生只能取消本人的 `pending` 预约，且 `now < start_at`。
- 管理员可以取消本人的或其他人的 `pending` 预约，原因必填，长度为 2-255 字。
- 已签到预约第一版不允许取消；如后续需要处理中途离场或设备故障，应新增独立异常终止状态，不能复用 `cancelled`。
- 已取消、已完成和已失约预约不能再次取消。
- 接口使用条件更新 `WHERE id = ? AND status = ?`，受影响行数为 0 时返回 `409 CONFLICT`。
- 取消成功后座位立即重新进入可用性查询，每日有效预约次数同步释放。
- 学生正常取消不生成违约；管理员取消不生成违约。
- 管理员的取消与资源状态变更记录审计日志，审计与业务更新同事务提交。

### 5.4 签到

`POST /reservations/:id/check-in`

```json
{
  "roomId": 12,
  "nonce": "c4b5c43b-bdf6-4eed-8e0f-91461f8c49b2",
  "issuedAt": "2026-11-10T07:45:10+08:00",
  "expiresAt": null,
  "signature": "base64url-hmac"
}
```

请求体字段就是签名原文的字段，`signature = HMAC(roomId|nonce|issuedAt)`。`expiresAt` 固定为 `null`，仅保留字段以兼容旧客户端，服务端**不参与签名也不做任何过期判断**。校验顺序固定为：

1. 当前用户是预约人，否则 `403 FORBIDDEN`。
2. 预约状态为 `pending`，否则 `409 CONFLICT`（已签到提示重复签到，已失约提示无法签到）。
3. `now >= check_in_open_at`，否则 `409 CONFLICT` 并返回窗口开始时间。
4. 签到数据中的 `roomId` 与预约一致，否则 `409 CONFLICT`。
5. 重建签名串并做恒定时间比较，失败返回 `403 FORBIDDEN`。
6. `now <= check_in_deadline`，否则 `409 CONFLICT` 并返回窗口截止时间。
7. 条件更新预约 `WHERE id = ? AND status = 'pending'` 为 `checked_in`，受影响行数为 0 时回滚并返回 `409 CONFLICT`。
8. 插入唯一签到记录（`method=qr`、`nonce`、`business_date=reserve_date`），写状态日志，提交事务。

签到事务只操作“预约 -> 签到记录”，不获取用户锁；每日有效预约数在 `pending -> checked_in` 时不变，因此不需要用户锁。它与失约任务的竞争由第 7 步的条件更新裁决：两者都对同一预约行加排他锁，先提交者赢，后者的受影响行数为 0，不会出现覆盖写。

### 5.5 生成签到码

`GET /admin/check-in-codes?roomId=12`

权限：管理员。该路径不占用 `/admin/study-rooms` 前缀，避免与 [自习室与座位模块](./02-自习室与座位模块.md) 的管理员路由争抢同一前缀的挂载顺序。

签到码**长期有效，不设过期时间**。管理员页面每 60 秒重新请求一次，服务端每次生成新的 `nonce` 并返回新的一张图；换图只是让屏幕保持“活”的观感，**已经发出的码不会被作废**，学生截图保存后仍然可以签到。

这是有意的产品取舍：去掉过期时间换来了“随时扫码都能用”，代价是码一旦泄露就无法回收，签到核验退化为“拿到房间码 + 在自己的预约窗口内”两个条件。如果后续需要恢复防转发能力，应重新引入短时码或房间级轮换开关，而不是在现有码上打补丁。

`study_rooms.check_in_nonce` 记录最近一次展示的 nonce，仅用于排查（`check_ins.nonce` 可以对应到具体是哪一张码被使用），校验时不做比对。管理员页面离开后不再刷新，因此没有管理员或值班设备在线时无法出码，此时必须走 5.6 的人工核验通道。

响应只返回二维码原始 JSON 和生成时间，不返回 HMAC 密钥：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {
    "roomId": 12,
    "issuedAt": "2026-11-10T07:45:10+08:00",
    "payload": {
      "roomId": 12,
      "nonce": "c4b5c43b-bdf6-4eed-8e0f-91461f8c49b2",
      "issuedAt": "2026-11-10T07:45:10+08:00",
      "expiresAt": null,
      "signature": "base64url-hmac"
    }
  }
}
```

签名原文采用稳定字段顺序：`roomId|nonce|issuedAt`。不得先把对象转成无序 JSON 后直接签名；`expiresAt` 固定为 `null` 且不参与签名。密钥来自 `CHECK_IN_SIGNING_SECRET`，与 JWT 密钥分离，长度至少 32 随机字节。

该响应设置 `Cache-Control: no-store`、`Pragma: no-cache`，禁止浏览器、代理和日志缓存完整签到载荷。码不设过期时间，服务端也不接受任何来自载荷的时间约束；唯一的限制是`学生的预约签到窗口`。

### 5.6 管理员人工核验签到

`POST /admin/reservations/:id/check-in`

二维码不可用（管理员页面无法访问、设备故障、学生手机无法扫码）时的降级通道，对应上位文档中的“管理员核验确认到场”。

```json
{
  "reason": "签到码页面故障，现场核对学号后手工签到"
}
```

规则：

- 仅管理员可调用，学生调用返回 `403 FORBIDDEN`。
- 只允许 `pending` 预约；已签到返回 `409 CONFLICT`，已失约不允许补签，返回 `409 CONFLICT`。
- 只允许在 `check_in_open_at <= now <= end_at` 区间内操作，避免提前放行或结束很久后补记。
- 原因必填，长度 2-255 字，写入 `check_ins.remark`，同时写审计日志。
- 写入签到记录 `method=manual`、`operator_id=当前管理员`、`nonce` 为空、`business_date=reserve_date`，并写状态日志（`actor_type=admin`、`actor_id`）。
- 人工核验不生成违约，也不修改预约签到窗口快照。
- 该接口不返回任何签到码数据。

### 5.7 管理员预约查询

`GET /admin/reservations` 支持 `dateFrom`、`dateTo`、`roomId`、`seatId`、`seatNo`、`studentNo`、`status`、`keyword`、`page`、`pageSize`，默认按开始时间倒序。

管理员不能通过该接口直接修改预约状态，所有业务动作必须走取消、签到、人工核验或定时状态转换服务。该接口必须使用服务端白名单排序字段，不能拼接 SQL。

## 6. 创建预约事务

并发安全不能依赖“先查询再插入”。按以下顺序实现：

```text
1. 校验参数与 Idempotency-Key；读取系统规则和注入的 now。
2. 查询该用户是否已存在同 key 的预约：参数一致则直接返回（200，replayed=true）；参数不同则返回 422。
3. 开启事务。
4. SELECT users FOR UPDATE；
   检查 active、违约限制、当日有效预约数（reserve_date = 目标日期，status IN ('pending','checked_in')）。
5. 以主键等值查询加锁：SELECT study_rooms ... FOR SHARE、room_time_slots ... FOR SHARE；
   检查自习室 open、时段 active、时段归属该自习室，且 room/slot 的 `bookable_from <= reserveDate`。
6. 由 reserveDate + slot 生成 startAt/endAt 与 check_in_open_at/check_in_deadline；
   检查日期范围、startAt 晚于 now。
7. SELECT seats FOR UPDATE；
   获得锁后重新读取座位状态、座位是否属于该自习室、座位 `bookable_from`，检查 available。
8. 查询该座位在 [startAt, endAt) 内的 pending/checked_in 预约；
   存在则回滚并返回 409。
9. 查询该用户在同区间内的 pending/checked_in 预约；
   存在则回滚并返回 409。
10. 插入预约（含快照、窗口、idempotency_key）；
    `active_slot_key` 冲突回滚并返回 409；
    `(user_id, idempotency_key)` 冲突说明并发的同键请求已经成功，回滚后按 §5.1 的重放语义返回已有预约。
11. 写入初始状态日志 from=null,to=pending（依赖 UNIQUE(reservation_id,to_status) 保证唯一）。
12. 提交事务，返回预约摘要和签到窗口。
```

统一锁顺序为“用户 -> 自习室 -> 时段 -> 座位”，所有路径都必须遵守。自习室和时段使用共享锁，使多个座位可以并发预约，同时阻止管理员在事务期间关闭资源或修改时段。管理员资源维护使用排他写锁并遵守相同顺序。

锁的两条实现要求：

- 自习室和时段必须用**主键等值查询**加锁。用 `WHERE room_id = ?` 之类范围条件加 `FOR SHARE` 会在 `REPEATABLE READ` 下产生间隙锁，让同一房间不同座位的预约互相阻塞甚至死锁。
- 取消也必须按“用户 -> 预约”顺序先锁 `users` 行再更新预约，使每日有效预约数的统计与写入严格串行。否则“取消”与“创建”并发时计数可能偏保守，产生一次误拒。

用户每日预约数查询条件：

```text
user_id = currentUser
reserve_date = requestedDate
status IN ('pending', 'checked_in')
```

时间重叠判断（半开区间）：

```text
existing.start_at < requested.end_at
AND existing.end_at > requested.start_at
```

起止时间正好相等不算冲突。例如 `08:00-10:00` 与 `10:00-12:00` 可以并存。

资源交叉归属必须显式校验：`slot.room_id = roomId`、`seat.room_id = roomId`、`room.id = roomId`。任一项不匹配返回 `422 VALIDATION_ERROR`，不进入后续检查。不要仅依赖“创建时已验证”这句话。

取消事务同样按“用户 -> 预约”顺序先锁 `users` 行再更新预约，使每日有效预约数的统计与写入严格串行；学生取消必须把 `now < start_at` 写进 `WHERE` 条件或在校验后立即更新，避免边界上被判为“开始后取消”。

## 7. 状态机

```text
pending
  ├─ 学生（开始前）或管理员取消 -> cancelled
  ├─ 系统停机豁免 -> cancelled（actor=system，不计违约）
  ├─ 签到窗口内签到 -> checked_in
  └─ 超过 check_in_deadline -> no_show

checked_in
  └─ 到达 end_at -> completed

completed / cancelled / no_show
  └─ 终态，不再转换
```

| 当前状态 | 动作 | 目标状态 | 操作者 |
| --- | --- | --- | --- |
| `pending` | 开始前取消 | `cancelled` | 本人 |
| `pending` | 任意时点取消并填写原因 | `cancelled` | 管理员 |
| `pending` | 签到窗口内扫码签到 | `checked_in` | 本人 |
| `pending` | 签到窗口内管理员人工核验 | `checked_in` | 管理员 |
| `pending` | 超过签到窗口 | `no_show` | 定时任务 |
| `pending` | 超过窗口且已过停机豁免阈值 | `cancelled` | 定时任务 |
| `checked_in` | 到达结束时间 | `completed` | 定时任务 |

每次状态转换使用 `WHERE id = ? AND status = 当前状态` 条件更新，并在同一事务中向 `reservation_status_logs` 写入一条业务事件；`UNIQUE(reservation_id, to_status)` 兜底防止重复日志。

### 7.1 失约之后的座位口径

失约发生在 `check_in_deadline`（`start_at + 15 分钟`），此时该时段已经开始，其他学生无法再预约同一时段（创建接口要求 `start_at > now`）。因此：

- **失约不释放该时段的可预约性。** 座位从失约时刻到时段结束保持空闲，也不会出现在任何人的可预约结果里。
- 这与“学生取消后座位立即释放”并不矛盾：取消只能发生在开始之前，此时时段尚未开始。
- 空闲造成的容量浪费会体现在 [统计与报表模块](./06-统计与报表模块.md) 的利用率下降中，因为计划容量分母在 `00:05` 已冻结，不因失约追溯减少。
- 第一版不实现“中途预约剩余时段”。若以后要支持，必须先支持分钟级时段切分，属于独立需求。

前端必须据此展示：失约预约不再提供“重新预约此时段”的入口，只展示原因和违约结果。

## 8. 定时任务

任务每分钟运行一次，`now` 由调度器注入并作为查询参数，使用条件更新保证幂等。所有 SQL 中的时间比较都把常量放在运算右侧，例如 `check_in_deadline < :now - INTERVAL 30 MINUTE`，不在列上做函数或算术运算。

### 8.1 超时未签到

候选查询：

```sql
SELECT id, user_id, check_in_deadline
FROM reservations
WHERE status = 'pending'
  AND check_in_deadline < :now
ORDER BY check_in_deadline
LIMIT 200;
```

对每条候选记录分两种处理：

- `:now - check_in_deadline <= 30 分钟`：正常失约。
- `:now - check_in_deadline > 30 分钟`：判定为任务曾中断，转为 `cancelled`，不生成违约。

正常失约流程（候选记录已在事务外读出，以下步骤在单条事务内执行）：

1. `SELECT users FOR UPDATE`，锁定该用户的用户行。
2. `UPDATE reservations SET status='no_show' WHERE id=? AND status='pending'`，受影响行数为 0 时回滚并跳过。
3. 写入 `no_show` 状态日志。
4. 调用 [违约管理模块](./04-违约管理模块.md) 的 `createFromNoShow(reservationId)`，由其负责插入违约、重算有效违约数和限制区间；本模块不得自行计算阈值或限制截止时间。
5. 提交事务。

停机豁免流程，同一事务内：

1. `UPDATE reservations SET status='cancelled', cancel_reason='签到服务中断期间到期，不计违约', cancelled_at=:now WHERE id=? AND status='pending'`。
2. 写入状态日志，`from=pending`、`to=cancelled`、`actor_type=system`、`actor_id=null`、`reason` 同上。
3. 不生成违约，不修改用户限制区间。
4. 提交后累加告警计数并输出 `job.degraded` 事件，供管理员在预约管理中复核。

阈值 30 分钟是固定常量。日常每分钟运行时，候选记录的 `check_in_deadline` 与本轮 `:now` 的差值不会超过 2 分钟，因此只有真实停机才会命中第二条分支。这样既不会在停机后批量误记违约，也不需要额外的任务状态表。

### 8.2 已签到完成

```sql
UPDATE reservations
SET status = 'completed'
WHERE status = 'checked_in'
  AND end_at <= :now
```

批量更新后必须为每条受影响记录写状态日志（可用 `INSERT ... SELECT` 在同一事务中写入，依赖 `UNIQUE(reservation_id, to_status)` 幂等）。重复执行不会影响已完成记录。

### 8.3 执行策略

- 每次批量处理数量限制为 200 条，循环至没有待处理记录或达到安全上限（例如 20 轮）。
- 记录扫描数、更新数、失败数和耗时；失败只记录错误，下一分钟整体重试，不允许单条异常中断整批。
- 单条记录失败只计入告警，不得中断整批，也不得让失败记录永久阻塞后续记录：候选查询按 `check_in_deadline` 升序分页读取，失败项在本轮跳过，下一轮重新进入候选。
- 若同一批候选连续 3 轮全部失败，输出 `job.degraded` 并结束本轮循环，等待人工处理，避免每分钟空转。
- 服务多个实例时使用数据库条件更新保证幂等；第一版不引入独立分布式锁。
- 任务不得在长事务中调用外部网络服务。

## 9. 前端交互

### 9.1 预约确认

- 页面传入房间、时段和座位，进入确认页后重新展示摘要。
- 提交时生成并复用 `Idempotency-Key`，按钮在请求中禁用。
- 成功后显示预约编号、签到窗口和查看详情入口。
- 409 冲突时刷新座位图，并明确提示“座位刚刚被其他同学预约”。
- 请求超时重试必须复用同一个 `Idempotency-Key`，避免用户看到自己刚创建的预约被当成冲突。

### 9.2 我的预约 `/reservations`

- 使用状态标签筛选：待签到、已签到、已完成、已取消、已失约。
- 待签到预约显示签到窗口和签到按钮；窗口外按钮禁用并解释原因。
- 已失约预约展示“已失约，该时段不再放出”，不提供重新预约入口。
- 已结束预约显示结果，不显示取消按钮。
- 分页切换时保留筛选条件。

### 9.3 预约详情 `/reservations/:id`

- 顶部显示状态与核心时间。
- 时间线展示创建、签到、取消、失约或完成事件；系统豁免取消需要单独文案，不能显示成“学生自己取消”。
- 签到面板提供三条入口，命中任一条后自动提交：
  1. **摄像头扫码**：`getUserMedia` 取视频流，逐帧用 `jsqr` 解码；
  2. **图片识别**：上传后台二维码截图解码，桌面浏览器也能完成签到；
  3. **粘贴/剪贴板**：手动粘贴签到 JSON，或读取剪贴板。
- 摄像头不可用（无设备、拒绝授权、非安全上下文）时必须降级到后两条，并给出可执行的提示文案，不能把签到卡死。
- 二维码无效、被篡改、自习室不匹配、不在窗口内时显示不同文案，具体业务错误由后端返回。
- 已失约的预约不显示签到入口。

### 9.4 管理员预约管理

- 默认按当日和未来预约倒序展示。
- 支持按学生学号、房间和状态筛选。
- 取消操作需输入原因并二次确认。
- 待签到预约提供“人工核验签到”入口，必须填写原因，成功后刷新详情。
- 详情中从状态日志展示创建、签到（含方式）、取消、失约和完成时间。
- 自习室和座位展示优先使用预约中的名称、位置、编号快照。
- 签到码页面只允许管理员访问，每 60 秒自动换一张图，并标注“长期有效、不会过期”。

## 11. 测试用例

### 11.1 创建与取消

1. 选择有效资源后创建预约成功，状态为 `pending`，`checkInWindow` 与快照一致。
2. 两个并发请求预约同一座位同一时段，只有一个成功。
3. 同一学生并发预约同一时间的不同座位，只有一个成功。
4. 相邻时段可预约，重叠时段被拒绝，边界相等不算重叠。
5. 当日已有 2 条有效预约时第 3 条被拒绝。
6. 违约限制期内创建预约被拒绝，并返回限制截止时间。
7. 开放时间之前的取消成功，座位可被他人预约，每日次数释放。
8. 开始后学生取消失败，管理员填写原因后成功。
9. 重复取消返回冲突且不改变原记录。
10. 已签到预约请求取消时返回冲突且不改变预约状态或签到记录。
11. 同一 `Idempotency-Key` 重放返回同一预约，`replayed=true`，不新增记录、不重复计次；同键换座位提交返回 422。
12. 不同用户使用相同 `Idempotency-Key` 互不影响。
13. 座位不属于该自习室、时段不属于该自习室时返回 422，不写入任何记录。
14. 资源未到 `bookable_from` 时，直接构造请求返回 409。
15. 学生调用管理员接口、查看或取消他人预约返回 403。

### 11.2 时间与边界

16. 预约日期使用本地日历日；服务端 `23:59` 创建的预约（`reserve_date` 为当天）不因 UTC 日期不同而落到前一天。
17. 签到窗口快照与 `start_at` 的关系满足 `check_in_open_at = start_at - 30min`、`check_in_deadline = start_at + 15min`。
18. 时段开始时间早于 `00:30` 时，签到窗口跨到前一自然日，签到记录的 `business_date` 仍等于 `reserve_date`。
19. `now = check_in_deadline` 允许签到，`now = check_in_deadline + 1s` 拒绝签到。
20. 调整窗口常量（或启用预留配置键）后，已创建预约的 `check_in_open_at`、`check_in_deadline` 不随之变化，历史窗口仍按快照解释。

### 11.3 签到与状态任务

21. 签到窗口内有效签到码签到成功。
22. 窗口开始前、结束后签到失败。
23. 伪造签名、篡改 roomId、其他自习室的二维码签到失败；换图前发出的旧码在换图后仍然签到成功。
24. 同一预约重复签到失败，签到记录只有一条。
25. 超过 `check_in_deadline` 的任务首次执行转为 `no_show`，并生成一条违约记录。
26. 任务重复执行不会生成重复违约记录，也不会写第二条状态日志。
27. 任务停机 2 小时后恢复，中断期间到期的 `pending` 转 `cancelled`，不生成任何违约，并输出告警。
28. 任务停机后恢复，仍在 30 分钟内的记录正常转 `no_show`。
29. `checked_in` 到达结束时间后转为 `completed`。
30. 已取消预约不会被任务改为失约。
31. 每个预约状态均能通过状态日志还原完整时间线。
32. 管理员人工核验签到成功，记录 `method=manual` 和 `operator_id`，写审计；已失约预约的人工核验被拒绝。
33. 失约后该时段不能被任何人重新预约，座位图显示空闲但提交返回冲突。

### 11.4 权限、并发与页面

34. 学生不能查看或取消他人预约。
35. 学生不能调用管理员列表、签到码和人工核验接口。
36. 座位图冲突后刷新，页面显示最新占用状态。
37. 请求失败、空列表和分页边界显示正确。
38. 创建预约后修改房间名称或座位编号，历史预约仍显示创建时的资源名称。
39. 签到码接口响应不能被浏览器缓存；时钟偏差超过 5 秒的载荷签到失败。
40. 用户创建新预约与自身旧预约转失约并发时，按用户锁串行，每日次数和限制结果可重复。
41. 同一学生并发“取消一条 + 创建一条”时，有效预约数不会超过上限。
42. 取消与创建并发不产生死锁（锁顺序均为用户 -> 预约）。
43. 同一房间不同座位的并发预约不因间隙锁互相阻塞。

### 14.4 已知缺口

1. **违约落库未接**：`NoopViolationPort` 只记录日志，M04 实现后替换注入即可，`reservations` 的失约状态与时间线已完整。
2. **`el-select` 类型不兼容**：当前 `element-plus 2.14.7` + `vue-tsc 3.3.14` 下 `ElSelect`/`ElOption` 的 props 类型无法解析（报 `PropType` 对象不可赋值），后台两个筛选器改用原生 `select`，样式与主题变量一致；后续升级依赖后可换回。
3. **并发用例未自动化**：座位行锁与唯一键的并发行为通过接口脚本验证，尚未加入 `node:test`（缺少测试库夹具）。
4. **统计口径**：`daily_slot_metrics` 属 M06，本模块只保证 `no_show`、`completed` 状态与 `business_date` 正确。
5. **演示数据**：开发库存在 `demo_student`、`demo_student2`、`demo_admin` 账号与若干预约记录，清理时按 `reserve_date` 与 `user_id` 处理。
6. **程序化组件样式**：`ElMessage`、`ElMessageBox` 由脚本调用，`unplugin-vue-components` 不会为它们注入样式，已在 `frontend/src/main.ts` 显式引入 `message`、`message-box` 的 `style/css`；新增其他程序化 API（如 `ElNotification`）时需要同样处理。
7. **扫码依赖设备**：摄像头扫码只能在真机（或带摄像头的设备）演示，桌面环境实测走“上传二维码图片”通道；解码统一用 `jsqr`，未接入 `BarcodeDetector`（各浏览器支持不一致）。`getUserMedia` 需要安全上下文，生产必须 HTTPS。
8. **查验能力退化**：签到码永久有效后，无法凭“码是新的”证明学生在场，只能靠预约窗口约束。若答辩时被问到防代签，应说明这是产品取舍，并给出“恢复短时码”或“房间级轮换开关”的演进方案，见 5.5。
