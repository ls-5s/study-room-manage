> 模块编号：M03

## 1. 模块目标

预约与签到模块是系统的核心业务闭环，负责将可预约座位转换为有明确时间范围和使用状态的学生预约。

模块需要同时解决四类问题：

1. 资源竞争：同一座位同一时段不能出现两条有效预约。
2. 用户冲突：同一学生不能同时预约两个座位，也不能无限囤积预约。
3. 状态流转：预约必须按照待签到、已签到、已完成、已取消或已失约转换。
4. 到场核验：学生只能在签到窗口内使用指定自习室的有效签到码完成签到。

## 2. 核心规则

| 规则 | 默认值 | 配置方式 |
| --- | --- | --- |
| 可预约提前天数 | 今天及未来 6 天，共 7 天 | 系统设置，最大 30 天 |
| 学生每日有效预约上限 | 2 条 | 系统设置 |
| 签到窗口开始 | 预约开始前 30 分钟 | 系统设置，第一版固定 |
| 签到窗口结束 | 预约开始后 15 分钟 | 系统设置，第一版固定 |
| 二维码有效期 | 60 秒 | 第一版固定常量 |
| 重复签到 | 拒绝 | 固定规则 |
| 开始后学生取消 | 拒绝 | 固定规则 |
| 管理员取消 | 必须填写原因 | 固定规则 |

有效预约仅指 `pending` 和 `checked_in`。已取消、已完成和已失约不占用每日预约次数，也不阻止新的不重叠预约。

房间、时段和座位还必须满足 `bookable_from <= reserveDate`。资源展示与预约创建调用同一个资源生效判断，不能把“次日生效”只写在前端。

## 4. 数据设计

### 4.1 `reservations`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 预约 ID |
| `user_id` | BIGINT UNSIGNED | 外键、非空 | 预约学生 |
| `room_id` | BIGINT UNSIGNED | 外键、非空 | 自习室 ID |
| `seat_id` | BIGINT UNSIGNED | 外键、非空 | 座位 ID |
| `slot_id` | BIGINT UNSIGNED | 外键、非空 | 开放时段 ID |
| `room_name_snapshot` | VARCHAR(64) | 非空 | 创建预约时的自习室名称 |
| `seat_no_snapshot` | VARCHAR(32) | 非空 | 创建预约时的座位编号 |
| `reserve_date` | DATE | 非空 | 预约业务日期 |
| `start_at` | DATETIME | 非空 | 预约开始时间快照 |
| `end_at` | DATETIME | 非空 | 预约结束时间快照 |
| `status` | ENUM | 非空 | 五种预约状态 |
| `cancel_reason` | VARCHAR(255) | 可空 | 取消原因 |
| `cancelled_by` | BIGINT UNSIGNED | 可空 | 取消操作人 |
| `cancelled_at` | DATETIME | 可空 | 取消时间 |
| `created_at` | DATETIME | 非空 | 创建时间 |
| `updated_at` | DATETIME | 非空 | 更新时间 |

`room_id`、`seat_id`、`slot_id` 冗余在预约表中是刻意的：直接查询方便，且创建时已验证座位属于自习室、时段属于自习室。名称和编号快照用于历史展示，资源之后改名不会改变学生已创建预约的描述。相关外键和 `seat-availability` 服务再次保证一致性。

### 4.2 `check_ins`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 签到记录 ID |
| `reservation_id` | BIGINT UNSIGNED | 唯一、外键 | 对应预约 |
| `checked_in_at` | DATETIME | 非空 | 实际签到时间 |
| `method` | ENUM | 非空 | 第一版固定 `qr` |
| `nonce` | CHAR(36) | 非空 | 二维码随机标识 |
| `created_at` | DATETIME | 非空 | 记录创建时间 |

`reservation_id` 唯一保证同一预约只有一条签到记录。签到成功后预约状态同时变为 `checked_in`，两者必须在同一事务中提交。

### 4.3 `reservation_status_logs`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 | 状态日志 ID |
| `reservation_id` | BIGINT UNSIGNED | 外键、非空 | 对应预约 |
| `from_status` | ENUM | 可空 | 创建记录时为空 |
| `to_status` | ENUM | 非空 | 转换后的状态 |
| `actor_type` | ENUM | 非空 | `user`、`admin`、`system` |
| `actor_id` | BIGINT UNSIGNED | 可空 | 系统任务时为空 |
| `reason` | VARCHAR(255) | 可空 | 取消或系统处理原因 |
| `occurred_at` | DATETIME | 非空 | UTC 状态转换时间 |

创建预约、取消、签到、失约和完成都必须在同一业务事务中写入状态日志。预约详情的时间线只读取该表，不使用可能被后续更新覆盖的 `reservations.updated_at` 推断历史。

索引：

- `reservation_status_logs(reservation_id, occurred_at)`。
- `reservation_status_logs(to_status, occurred_at)`，用于状态审计。

### 4.4 有效预约唯一键

建议增加数据库生成列：

```text
active_slot_key =
  CASE
    WHEN status IN ('pending', 'checked_in')
      THEN CONCAT(seat_id, ':', reserve_date, ':', slot_id)
    ELSE NULL
  END
```

并为 `active_slot_key` 建立唯一索引。MySQL 唯一索引允许多个 `NULL`，因此已取消、已完成和已失约历史不会妨碍后续预约。

该唯一键依赖开放时段不重叠。项目必须在时段维护服务中禁止同一自习室的有效时段重叠，并在迁移和测试中验证该约束；如果未来允许重叠，必须改用排他约束或专用锁表。

### 4.5 索引

- `reservations(user_id, reserve_date, status)`。
- `reservations(room_id, reserve_date, slot_id, status)`。
- `reservations(seat_id, reserve_date, status)`。
- `reservations(status, start_at, end_at)` 用于定时任务。
- `check_ins(checked_in_at)` 用于统计。

## 5. 接口设计

### 5.1 创建预约

`POST /reservations`

请求：

```json
{
  "roomId": 12,
  "seatId": 205,
  "reserveDate": "2026-11-10",
  "slotId": 31
}
```

响应：

```json
{
  "code": "OK",
  "message": "预约创建成功",
  "data": {
    "id": 1001,
    "roomId": 12,
    "seatId": 205,
    "seatNo": "A-01",
    "reserveDate": "2026-11-10",
    "startAt": "2026-11-10T08:00:00+08:00",
    "endAt": "2026-11-10T10:00:00+08:00",
    "status": "pending",
    "checkInWindow": {
      "startAt": "2026-11-10T07:30:00+08:00",
      "endAt": "2026-11-10T08:15:00+08:00"
    }
  }
}
```

### 5.2 查询预约

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| GET | `/me/reservations` | 学生 | 查询本人预约 |
| GET | `/reservations/:id` | 本人/管理员 | 查询预约详情 |
| GET | `/admin/reservations` | 管理员 | 多条件分页查询 |

学生列表筛选参数：

```text
status        pending/checked_in/completed/cancelled/no_show
dateFrom      YYYY-MM-DD
dateTo        YYYY-MM-DD
page
pageSize
```

管理员列表额外支持 `roomId`、`studentNo`、`seatNo` 和 `keyword`。列表只返回摘要；详情包含自习室、座位、签到窗口、签到记录和取消信息。

### 5.3 取消预约

`POST /reservations/:id/cancel`

学生请求：

```json
{
  "reason": "临时有课"
}
```

管理员请求：

```json
{
  "reason": "自习室设备故障，统一取消"
}
```

规则：

- 学生只能取消本人的 `pending` 预约，且当前时间必须早于 `start_at`。
- 管理员可以取消 `pending` 预约，原因必填，长度为 2-255 字。
- 已签到预约第一版不允许取消；如后续需要处理中途离场或设备故障，应新增独立异常终止状态，不能复用 `cancelled`。
- 已取消、已完成和已失约预约不能再次取消。
- 接口使用条件更新 `WHERE id = ? AND status = ?`，受影响行数为 0 时返回冲突。
- 取消成功后座位立即重新进入可用性查询。
- 学生正常取消不生成违约；管理员取消不生成违约。

### 5.4 签到

`POST /reservations/:id/check-in`

```json
{
  "roomId": 12,
  "nonce": "c4b5c43b-bdf6-4eed-8e0f-91461f8c49b2",
  "issuedAt": "2026-11-10T07:45:10+08:00",
  "expiresAt": "2026-11-10T07:46:10+08:00",
  "signature": "base64url-hmac"
}
```

服务端检查：

1. 当前用户是预约人。
2. 预约状态为 `pending`。
3. 当前时间位于签到窗口内。
4. 签到数据中的 `roomId` 与预约一致。
5. `issuedAt <= now <= expiresAt`，有效期不超过 90 秒。
6. HMAC 签名使用恒定时间比较，防止时序攻击。
7. 更新预约为 `checked_in` 并创建唯一签到记录。

### 5.5 生成签到码

`GET /admin/study-rooms/:roomId/check-in-code`

权限：管理员。第一版由管理员在后台页面生成并展示二维码。

响应只返回二维码原始 JSON 和展示截止时间，不返回 HMAC 密钥：

```json
{
  "roomId": 12,
  "payload": {
    "roomId": 12,
    "nonce": "c4b5c43b-bdf6-4eed-8e0f-91461f8c49b2",
    "issuedAt": "2026-11-10T07:45:10+08:00",
    "expiresAt": "2026-11-10T07:46:10+08:00",
    "signature": "base64url-hmac"
  }
}
```

签名原文采用稳定字段顺序，例如 `roomId|nonce|issuedAt|expiresAt`。不得先把对象转成无序 JSON 后直接签名。

该响应设置 `Cache-Control: no-store`、`Pragma: no-cache`，禁止浏览器、代理和日志缓存完整签到载荷。服务端允许不超过 5 秒的时钟偏差，但总有效期不得超过 65 秒。

### 5.6 管理员预约查询

`GET /admin/reservations` 支持日期、自习室、座位、学生、状态和关键字筛选，默认按开始时间倒序。管理员不能通过该接口直接修改预约状态，所有业务动作必须走取消或定时状态转换服务。

## 6. 创建预约事务

并发安全不能依赖“先查询再插入”。建议按以下顺序实现：

```text
1. 校验参数；读取系统规则和当前时间。
2. 开启事务。
3. SELECT users FOR UPDATE；
   检查 active、违约限制、当日有效预约数。
4. SELECT study_rooms FOR SHARE、room_time_slots FOR SHARE；
   检查自习室 open、时段 active、时段归属正确，且目标日期的 `bookable_from` 均已生效。
5. 根据 reserveDate + slot 生成 startAt/endAt；
   检查日期范围、开始时间晚于当前时间。
6. SELECT seats FOR UPDATE；
   获取锁后重新读取座位状态、资源归属和 `bookable_from`，检查座位 available。
7. 查询该座位在时间区间内的 pending/checked_in 预约。
8. 查询该用户在同一时间区间内的 pending/checked_in 预约。
9. 插入预约；唯一键冲突转换为 409。
10. 写入初始状态日志 `from=null, to=pending`。
11. 提交事务，返回预约摘要和签到窗口。
```

统一锁顺序为“用户 -> 自习室 -> 时段 -> 座位”。自习室和时段使用共享锁，使多个座位可以并发预约，同时阻止管理员在事务期间关闭资源或修改时段。管理员资源维护使用排他写锁并遵守相同顺序。取消、签到和定时任务使用状态条件更新，禁止在长事务内调用外部网络服务。

用户每日预约数查询条件：

```text
user_id = currentUser
reserve_date = requestedDate
status IN ('pending', 'checked_in')
```

时间重叠判断：

```text
existing.start_at < requested.end_at
AND existing.end_at > requested.start_at
```

起止时间正好相等不算冲突。例如 `08:00-10:00` 与 `10:00-12:00` 可以并存。

## 7. 状态机

```text
pending
  ├─ 学生或管理员取消 -> cancelled
  ├─ 签到窗口内签到 -> checked_in
  └─ 超过 start_at + 15 分钟 -> no_show

checked_in
  └─ 到达 end_at -> completed

completed / cancelled / no_show
  └─ 终态，不再转换
```

| 当前状态 | 动作 | 目标状态 | 操作者 |
| --- | --- | --- | --- |
| `pending` | 开始前取消 | `cancelled` | 本人 |
| `pending` | 任意时点取消并填写原因 | `cancelled` | 管理员 |
| `pending` | 窗口内签到 | `checked_in` | 本人 |
| `pending` | 超过签到窗口 | `no_show` | 定时任务 |
| `checked_in` | 到达结束时间 | `completed` | 定时任务 |

每次状态转换使用 `WHERE id = ? AND status = 当前状态` 条件更新，并在同一事务中向 `reservation_status_logs` 写入唯一业务事件。

## 8. 定时任务

任务每分钟运行一次，使用条件更新保证幂等。

### 8.1 超时未签到

```text
UPDATE reservations
SET status = 'no_show'
WHERE status = 'pending'
  AND start_at + 15 minutes < current_time
```

只有实际从 `pending` 更新为 `no_show` 的记录才触发违约记录写入。处理流程应在同一事务中：

1. 先无锁读取候选预约及其 `user_id`。
2. 开启事务并锁定该用户的 `users` 行。
3. 使用 `WHERE id = ? AND status = 'pending'` 条件更新预约，受影响行数为 0 时回滚并跳过。
4. 写入 `no_show` 状态日志。
5. 以 `reservation_id` 唯一约束创建违约记录。
6. 重算用户有效违约数和预约限制。

### 8.2 已签到完成

```text
UPDATE reservations
SET status = 'completed'
WHERE status = 'checked_in'
  AND end_at <= current_time
```

重复执行不会影响已完成记录。任务失败时记录错误日志，下一分钟重试；不允许因单条异常停止整批任务。

### 8.3 执行策略

- 每次批量处理数量可限制为 200 条，循环至没有待处理记录或达到安全上限。
- 记录扫描数、更新数、失败数和耗时。
- 服务多个实例时使用数据库条件更新保证幂等；第一版可不引入独立分布式锁。

## 9. 前端交互

### 9.1 预约确认

- 页面传入房间、时段和座位，进入确认页后重新展示摘要。
- 提交按钮在请求中禁用，避免双击。
- 成功后显示预约编号、签到窗口和查看详情入口。
- 409 冲突时刷新座位图，并明确提示“座位刚刚被其他同学预约”。

### 9.2 我的预约 `/reservations`

- 使用状态标签筛选：待签到、已签到、已完成、已取消、已失约。
- 待签到预约显示签到窗口和签到按钮；窗口外按钮禁用并解释原因。
- 已结束预约显示结果，不显示取消按钮。
- 分页切换时保留筛选条件。

### 9.3 预约详情 `/reservations/:id`

- 顶部显示状态与核心时间。
- 时间线展示创建、签到、取消、失约或完成事件。
- 签到面板支持扫描二维码或粘贴签到数据。
- 二维码无效、过期、自习室不匹配时显示不同文案，具体业务错误由后端返回。

### 9.4 管理员预约管理

- 默认按当日和未来预约倒序展示。
- 支持按学生学号、房间和状态筛选。
- 取消操作需输入原因并二次确认。
- 详情中从状态日志展示创建、签到、取消、失约和完成时间，签到记录用于补充签到方式。
- 自习室和座位展示优先使用预约中的名称、编号快照。
- 签到码页面只允许管理员访问，页面离开后停止自动刷新。

## 10. 异常处理

| 场景 | HTTP | 业务处理 |
| --- | --- | --- |
| 座位已被预约 | 409 | 返回冲突，不创建记录 |
| 用户已有重叠预约 | 409 | 返回时间冲突 |
| 当日有效预约超限 | 409 | 返回次数上限 |
| 违约限制中 | 403 | 返回限制截止时间 |
| 座位维修或自习室关闭 | 409 | 返回资源不可用 |
| 预约已开始 | 409 | 学生不能取消 |
| 已签到预约请求取消 | 409 | 第一版不支持取消已签到预约 |
| 管理员取消未填原因 | 422 | 字段校验错误 |
| 二维码过期 | 409 | 提示刷新签到码 |
| 二维码签名错误 | 403 | 提示签到码无效 |
| 不在签到窗口 | 409 | 返回允许签到的时间范围 |
| 重复签到 | 409 | 不创建第二条签到记录 |

## 11. 测试用例

### 11.1 创建与取消

1. 选择有效资源后创建预约成功，状态为 `pending`。
2. 两个并发请求预约同一座位同一时段，只有一个成功。
3. 同一学生并发预约同一时间的不同座位，只有一个成功。
4. 相邻时段可预约，重叠时段被拒绝。
5. 当日已有 2 条有效预约时第 3 条被拒绝。
6. 违约限制期内创建预约被拒绝。
7. 开放时间之前的取消成功并释放座位。
8. 开始后学生取消失败，管理员填写原因后成功。
9. 重复取消返回冲突且不改变原记录。
10. 已签到预约请求取消时返回冲突且不改变预约状态或签到记录。

### 11.2 签到与状态任务

11. 签到窗口内有效签到码签到成功。
12. 窗口开始前、结束后签到失败。
13. 过期、伪造、其他自习室的二维码签到失败。
14. 同一预约重复签到失败，签到记录只有一条。
15. 超过 `start_at + 15` 分钟的任务首次执行转为 `no_show`。
16. 任务重复执行不会生成重复违约记录。
17. `checked_in` 到达结束时间后转为 `completed`。
18. 已取消预约不会被任务改为失约。
19. 每个预约状态均能通过状态日志还原完整时间线。

### 11.3 权限与页面

20. 学生不能查看或取消他人预约。
21. 学生不能调用管理员列表和签到码接口。
22. 座位图冲突后刷新，页面显示最新占用状态。
23. 请求失败、空列表和分页边界显示正确。
24. 创建预约后修改房间名称或座位编号，历史预约仍显示创建时的资源名称。
25. 签到码接口响应不能被浏览器缓存，超过有效期或时钟偏差超过 5 秒的载荷签到失败。
26. 房间、时段或座位尚未到 `bookable_from` 时，直接构造预约请求也返回冲突。
27. 用户创建新预约与自身旧预约转失约并发时，按用户锁串行，预约限制结果可重复。
